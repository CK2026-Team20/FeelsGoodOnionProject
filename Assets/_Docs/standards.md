# 개발·협업 기준

## 작업 순서와 근거

사용자가 지정한 DryForge 스킬과 승인된 작업 범위를 따른다. 요구가 이미 명확한 작은 수정·읽기 전용 분석은 필요한 기준만 적용하고 전체 준비·이관 절차를 반복하지 않는다. 큰 변경은 명세·실행 계획·독립 검토를 적용한다. 명시적인 사용자 지시·소유권 제한과 충돌하면 사용자 지시를 우선하며 수정 권한을 넓혀 해석하지 않는다. 프로젝트 공통 문서는 프로젝트 루트 기준 Assets/_Docs/에서 읽고 작성·갱신한다. 루트 진입 지침과 모듈별 AGENTS.md의 위치는 바꾸지 않는다.

목표 → 참고 코드·자산 선택 → 제약 조건 → 완료 기준 순서로 작업 범위를 정한다. 목표가 없는 작업은 구현에 들어가지 않는다. 완료 기준은 기능 명세·코드 리뷰·테스트 및 검증 항목으로 추적 가능하게 기록한다. 기존 기능 변경은 사용자 승인 범위에서만 수행한다.

작업 전 `planning-index.md`에서 현재 지정 기획 버전과 직접 지시를 확인한다. 사용자의 최신 직접 지시와 최신 지정 기획서가 변경 목표를 정하며, 코드·씬·프리팹·설정은 현재 구현 상태와 차이를 확인하는 근거다. 구버전 README·과거 기획·이전 구현을 근거로 새 명세를 되돌리지 않는다. 문서 갱신 때 실제 내용을 다시 읽고 색상별 의미·변경 차이·검증 항목을 갱신한다. 향후 기능과 일정은 추측해 추가하지 않는다.

## 문서 갱신과 선택 읽기

현재 상태는 tracking/status.md, 열린 문제는 tracking/findings.md에 한 번만 기록하고 상세 증거로 연결한다. 과거 승인·검증·실패 기록은 날짜별 파일이나 archive에 보존하며 현재 규칙과 섞지 않는다. planning-index는 현재 원본·후속 지시·적용 범위를 소유하고 구현 완료 상태를 중복 관리하지 않는다. 지역 지침은 모듈 고유 책임·예외·검증을 담고 상위 공통 규칙을 복사하지 않는다. 독립 하위 작업에는 관련 상위 지침과 security의 승인 예외를 함께 전달한다.

작업 문서 정본 한 벌만 읽고 도구용 사본은 해시로 동기화를 확인한다. 작업 내부 구현 순서는 조정할 수 있으나 작업 간 의존 관계·재생성 순서를 실행자가 임의로 재판단하지 않는다. 변경이 필요하면 영향받는 실행을 멈추고 이유를 설명한 뒤 계획을 갱신하고 그래프·의존 관계를 다시 검증한다. 승인된 기능·권한·완료 범위가 달라지는 경우 사용자에게 변경 결정을 받는다. 최신 규칙이 바뀌면 소비하는 지역 지침도 같은 변경에서 갱신한다.

## 소유권과 의존성

- 수정은 현재 작업자 소유 경로 안에서 수행한다. 참조 허용에는 타 작업자 공개 API·이벤트 사용과 자기 소유 오브젝트의 컴포넌트 추가·설정·연결, 소유 배치 override 저장이 포함된다. 타 작업자 원본 코드·씬·프리팹·.meta·import 설정 직접 수정과 원본 Apply·이동·삭제·GUID 변경은 명시적 파일 허용 없이는 금지한다.
- 비아트 작업자는 _Art 원본을 수정하지 않는다. 현재 Tech_SYM의 루트 지침·Assets/_Docs 문서 작업 예외를 기존 PDF·공용 코드·ProjectSettings·Packages 수정 허가로 확대하지 않는다.
- 상태의 권위 있는 소유자는 하나다. PlayerModel 상태를 UI나 세션 캐시에 별도 원본으로 복제하지 않는다. 체크포인트 스냅샷과 현재 플레이어 수치는 서로 다른 수명과 목적을 가진다.
- 도메인 규칙, 입력·유스케이스, 화면, 외부 연동 책임을 분리한다. 파일 분할이나 partial 분할만으로 책임 분리가 되었다고 판단하지 않는다.
- 조합을 우선하고 실제 대체 가능한 관계에만 상속한다. 교체·검증·외부 연동 경계에는 작은 계약을 두되 구현마다 인터페이스·팩토리를 의무적으로 추가하지 않는다.
- 전역 가변 상태와 거대 싱글턴을 기본 구조로 추가하지 않는다. 현재 서비스 등록과 조립은 구성 지점에서 처리하고 View가 서비스 탐색으로 업무 처리를 우회하지 않는다.
- 같은 기능의 버튼·키·드래그는 같은 명령으로 연결한다. 외부 입력 검증은 경계에서 수행하며 도메인 불변식과 필요한 독립 검증은 유지한다.
- 실패는 성공처럼 반환하거나 무시하지 않는다. 복구 여부와 작업 문맥을 기록하며 민감정보는 로그에 넣지 않는다.

## Inspector 설명

2026-10-06 사용자 직접 지시. 모든 Inspector 직렬화 필드에 쉬운 한국어 Tooltip을 제공한다. private SerializeField뿐 아니라 public 직렬화 필드, bool·열거·참조·배열과 중첩 데이터도 대상이다. Inspector에 표시되지 않는 실행 캐시·결과 기록용 데이터에는 기계적으로 속성을 붙이지 않는다. 보호 원본은 누락을 보고하고 허가 없이 수정하지 않는다.

설정의 용도를 먼저 설명하고 필요한 단위·좌표 기준·증감 결과·0의 의미를 덧붙인다. 참조 필드는 어떤 오브젝트나 자산을 연결하는지 설명한다. 기즈모가 있으면 실제 색상과 표시 내용을 함께 적는다. 예: `[Tooltip("플레이어가 정렬될 위치를 트리거 기준으로 지정합니다. 파란색 기즈모로 표시됩니다.")]`. 변수 이름을 풀어 쓰거나 코드 용어만 나열하는 설명은 피한다. 변경 시 실제 직렬화 값·계산·기즈모·자산 연결과 설명의 일치를 확인한다.

## HMS·SYM 조립과 소스 정리

HMS와 SYM 기능을 조립하기 전에 의미가 같은 상태·입력·물리·화면 출력의 소유자를 한 명으로 정한다. 공개 API·이벤트, 실행 수명, 씬·프리팹 배치, 코드 호출과 GUID·직렬화 참조를 비교한다. HMS로 완전히 대체할 수 있으면 SYM 소유 배치에서 연결을 이관하고 중복 SYM 구현·호환 필드·조립 참조를 제거한다. 부분 대체라면 남는 책임과 이유를 기록한다. 이름이나 미래의 재사용 가능성만으로 공통화하지 않는다.

현재 HMS는 플레이어 입력·폼·이동·애니메이션 선택과 Cinemachine 모드를 소유한다. SYM의 세션 Actor 수명, 모달 입력 차단, 카메라 정렬·전환 완료, 발판 운반, HeavyState의 무게 표시는 별도 책임이다. 기존 TearFragment의 상한 시 소비와 LevelTearFragment의 상한 시 보존도 서로 다른 정책이다. 부모 로컬 경로를 사용하는 SYM 선형 발판을 월드 오프셋·끝점 대기 정책이 다른 HMS MovingPlatform으로 임의 대체하지 않는다.

임시 더미·중복·테스트 소스를 제거할 때 코드·문자열·메뉴·동적 등록·자산 GUID·직렬화 참조와 공개 계약을 확인한다. 자기 소유 자산은 Unity API로 원본과 .meta를 함께 삭제하고 빈 폴더도 같은 방식으로 정리한다. 런타임 기능, 실제 자산 작성 도구, Play 진입과 빌드 도구는 테스트 전용 코드와 구분해 유지한다. 제거 후 컴파일·Missing Script·중요한 결합 기능을 확인한다. 일회성 외부 검증 스크립트는 실행 후 제거하고 케이스·명령·결과·삭제 근거를 보존한다. 테스트 소스 삭제는 검증 생략이나 과거 증거 삭제를 뜻하지 않는다.

## UI와 수명

View는 주입받은 ViewModel의 상태·Command 또는 공개 메서드에 연결한다. ViewModel은 View를 직접 참조하지 않는다. View가 전역 싱글턴이나 구체 Model을 검색해 업무를 처리하지 않는다. 순수 표시·애니메이션은 View가 담당할 수 있다.

Bind/Unbind, OnEnable/OnDisable/OnDestroy, 풀 반환의 소유권을 명시한다. 재바인딩은 자기 구독만 해제하며 다른 소비자의 리스너를 일괄 삭제하지 않는다. 비동기 작업은 수명과 연결된 취소를 제공하고 폐기 후 콜백을 차단한다. 양방향 바인딩은 상태 갱신이 다시 명령을 호출하는 루프를 막는다.

입력 한 번당 명령 한 번, 재바인딩 중복 없음, 폐기 후 호출 없음, 기존 ViewModel 로직 재사용을 검증한다. 현재 코드의 예외나 위반을 발견해도 문서상 준수를 선언하거나 범위 밖에서 전체 재작성하지 않는다.

## Unity 자산과 배치

새로 구성하는 완성 오브젝트는 빈 GameObject를 최상위 루트로 둔다. 루트는 제어·공통 데이터, 자식은 Visual·CameraAnchor·VFX·SFX·Collider의 역할을 분리한다. Visual에 업무 스크립트를 몰아넣지 않는다. 같은 역할마다 별도 Canvas나 파일을 강제하지 않는다.

기존 물리 계약 때문에 Facade·Rigidbody·Collider가 같은 ActorBody에 있어야 하는 경우, 빈 PlayerRoot 아래 ActorBody로 묶인 현재 구조를 유지하고 차이를 명시한다. 기존 붕괴 발판처럼 같은 오브젝트의 Collider를 요구하는 구현도 승인 없이 이동하지 않는다. 기존 자산 전체가 새 배치 기준을 만족한다고 주장하지 않는다.

자산 이동·이름 변경으로 GUID 참조를 깨뜨리지 않는다. 원본과 .meta를 함께 검토한다. 설정 수치·문구·리소스 ID는 목적에 맞는 데이터로 관리하고 의미가 같은 반복값만 공통화한다. 단순 재사용 가능성만으로 다른 기능을 결합하지 않는다.

## 검증·산출물·Git

변경 기능의 상태 전이·오류·취소·외부 계약을 관찰 가능한 결과로 검증한다. 코드의 계산을 그대로 복사하는 테스트는 피한다. 가역적인 문서 수정에 게임 동작 테스트를 무조건 추가하지 않는다. 실제 실행하지 않은 테스트·빌드는 통과로 기록하지 않는다.

Unity 실행 변경에는 컴파일, Missing Script/직렬화 참조, 변경한 기능의 기존 씬 연결, 저장 상태와 diff 검토를 포함한다. 실제 프레임·물리·Unity 수명에 의존하는 기능은 해당 환경에서 자동 실행하고 관찰 가능한 요구 결과를 확인한다. 실제 빌드 화면의 플레이·UI/UX·재미 평가는 아래 분담에 따라 인계할 수 있으며 인계한 항목은 확인 전까지 미검증이다. 별도 검증용 씬으로 요청된 기존 씬 검증을 대체하지 않는다. 타인 씬의 미저장 변경을 자동 저장하지 않는다.

코드 리뷰·테스트 검증 문서와 실제 프로젝트 자산을 제외한 출력은 output/Tech_SYM/아래 종류·기능별로 분류한다. 루트 지침과 Assets/_Docs의 프로젝트 Markdown 및 대응 메타데이터는 승인된 문서 위치 예외다. 검토·검증 기록은 Assets/_Docs/tracking, 결정 기록은 그 하위 decisions에 둔다. 기존 Assets/_Docs PDF와 그 메타데이터는 보존한다. output은 Git ignore 대상이므로 공유 문서의 유일한 보관처로 쓰지 않는다.

커밋·푸시·PR·병합은 해당 작업의 명시적 허용 범위를 따르며 문서 작성 요청으로 자동 수행하지 않는다. 생성물·관계없는 .meta·패키지·프로젝트 설정이 diff에 섞였는지 확인한다. 동일 소스·자산·설정·도구 환경에 대한 통과 결과는 그 범위를 확인한 뒤 재사용하며 새 변경·실패·환경 차이 없이 같은 검사를 반복하지 않는다. 임시 호환 코드에는 이유와 제거 조건을 남기고, 사용되지 않는 코드도 참조와 호환 영향을 확인한 뒤 승인 범위에서 제거한다.

2026-10-06 후속 지시로 앞선 미커밋 변경과 앞으로 자동 저장으로 추가되는 변경도 전부 커밋 대상이다. Unity·Editor가 저장한 자산·설정은 원인, 변경 시점, 기준점과 현재 diff를 검토·기록하고 기능별 커밋에 포함한다. 자동 변경을 정리 이유로 원복하지 않는다. 보호 원본의 수동 변경은 여전히 별도 파일 허가가 필요하며, Library·Temp·output 등 기존 ignore 대상은 저장소 산출물로 바꾸지 않는다.

## 기능 테스트와 QA 인계
