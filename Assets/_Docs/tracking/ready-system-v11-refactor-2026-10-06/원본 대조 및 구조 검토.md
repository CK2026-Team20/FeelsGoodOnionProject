## CameraRig가 PlayerRoot 안에 있었던 이유

저장된 CameraRig는 PlayerRoot 아래에서 ActorBody와 **형제**다. ActorBody가 Rigidbody로 움직이고 PlayerRoot는 생성 Pose에 남으므로, 단순히 플레이어 이동을 부모 Transform으로 따라가게 만든 구조라고 설명하면 틀리다.

```text
최초 조회 PlayerRoot (그때 비활성 prefab)
├─ ActorBody (실제 움직이는 Rigidbody, Facade 등)
│  ├─ VisualRoot
│  └─ CameraAnchor
└─ CameraRig
   ├─ MainCamera (Camera, Brain, HMS Controller)
   └─ Side / Quarter / Back / BackFixed
```

HMS PlayerCameraController는 Awake에서 이동 모드와 서로 다른 네 가상 카메라 참조를 검사하고, OnEnable에서 ModeChanged를 구독한다. 공개 재연결 API가 없다. 기존 SessionActorHost는 비활성 prefab 안에서 참조를 미리 연결하고 첫 활성화 때 Awake/OnEnable을 함께 통과시키기 위해 카메라와 Actor를 같은 생성 단위에 묶었다. retry에도 같은 단위를 새로 만들면 파괴된 Actor 참조를 새 리그가 들고 있지 않는다는 수명상 이점이 있었다. [당시 수명 결정](../decisions/0004-actor-camera-lifetime.md)의 구현 근거와 일치한다.

이 이유는 당시 공개 API의 제한과 해제 안전성에 대한 설명이다. PlayerRoot 자식이 Cinemachine의 필수 조건이라는 뜻은 아니다. 설치 패키지의 `Documentation~/CinemachineBrain.md`와 `CinemachineCamera.md`에서도 Brain이 Unity Camera의 출력을 갱신하고 별도 가상 카메라 중 우선순위를 선택하는 역할을 확인했다. 같은 역할의 공개 설명은 [Unity Cinemachine Brain 문서](https://docs.unity3d.com/Packages/com.unity.cinemachine@3.1/manual/CinemachineBrain.html)에 있다. 설치 패키지 version은6.6.0이며 링크의 버전 문자열을 설치 버전이라고 쓰지 않는다.

단일 출력과 분리 리그에서는 HMS에 명시적 Bind/Unbind·미리 선택/완료 후 확정 계약을 추가한다. App 출력은 살아 있고 Core의 두 가상 카메라는 새 Actor 목표를 받는다. LevelCameraService는 요청/입력 차단/Side Z정렬/Brain 완료만 담당한다. ActorCameraRig는 이관 후 삭제하여 우선순위 작성자를 HMS 한곳으로 만든다. 먼저 새 모드로 물리 축을 바꾸면 블렌드가 끝나기 전에 이동 축이 바뀌므로 Preview와 Commit의 순서가 필요한 것이다.

## Bootstrap 카메라와 Core 카메라를 나눈 이유

현재 AppComposition의 BootstrapCamera는 검정 배경의 대기 출력이며, 실제 게임 출력은 Actor MainCamera다. **CoreLevelCamera라는 prefab 이름은 LevelCameraService의 구간 조정 객체이고 실제 출력 Camera가 아니다.** 실제 Unity Camera 두 개를 서로 켜고 끄는 구조와 Core 서비스 객체를 구분해야 한다.

분리의 당시 목적은 Actor가 없는 부트/제목/연출/재시도 준비 시간에도 출력과 AudioListener를 확보하는 것이었다. 실제 활성 출력 한 개를 만들기 위해 GameplayVisible/ActorViewReady 통지와 App 토글 구독이 추가됐다. 그 결과 재시도마다 출력/Listener를 교체하고, UI가 빌린 카메라 참조도 바꿔야 했다. 현재 Title·Options·HUD·Cinematic은 ScreenSpaceOverlay이므로 이 표시 요구에 두 출력의 교대가 구조적으로 필수인 것은 아니다.

새 목표는 앱에 한 Output을 두고 Core 리그만 준비/해제하는 것이다. Actor가 없을 때도 같은 출력은 유지하고 월드 렌더만 가린다. 별도 BootstrapCamera·Actor 출력 교대·GameplayOutputChanged를 위한 중복 분기를 제거한다. 실제 블렌드·초기 Actor 준비·옵션 정지라는 필요한 동작은 남긴다.

## 전체 시스템에서 유지하는 경계와 줄이는 계층

| 경계 | 현재 채택 이유 / 실제 필요성 | 줄일 대상과 채택 방법 |
|---|---|---|
| App / Core / Stage | 음량/출력은 판 사이에도 필요하고, 세션/능력/대화 장부는 한 판에 필요하며, 월드는 retry에 재준비됨 | 여섯 씬 분리는 유지. 한 거대 GameManager로 합치지 않고 ActorCamera 수명만 분리 |
| SessionActorHost / Bridge | 생성·파괴 소유와 빌린 HMS API 조정이 다름 | Host의 자식 카메라/기름 Scope 참조 삭제, Bridge의 백뷰/입력 기준·준비 잔재 정리 |
| Control 토큰 | 옵션과 메모/대화의 서로 다른 제한이 중첩됨 | 메모·대화 WorldPause만 제거. 전역 bool 해제로 바꾸지 않음 |
| Model / VM / View | 업무 상태, 화면용 명령/상태, 실제 표시의 변경 이유가 다름 | 중복 Prompt·거리 Instruction·표시 카드 제거. VM→View 직접 참조 없음 |
| StageService / 체크포인트 | Stage는 배치/트리거, Session은 위치/조각 두 값의 기록을 소유 | 새 월드 저장 계약/상태 등록자/객체별 ID를 만들지 않음. 사용자 직접 지시가 원본의 월드 상태 복원을 대체 |
| Contacts / Motor / 기능 컨트롤러 | 물리 콜백, 실제 위치 쓰기, 진행 목적/상태는 서로 다름 | 단일 물리 이동자 유지. HMS 공개 기능이 완전 동등하지 않은 XYZ/효과를 이름만으로 삭제하지 않음 |
| EnemyActor / StateMachine / Motor / Combat | root 조립, 배타적 전이, 지형 이동, 피해원은 실제 책임이 다름 | HP만 가진 EnemyModel·IState 파일·Float·사망 기름 제거. 스턴은 FSM 한 소유자 |
| 문/트레이/서랍 | 조작과 두 종점 동작의 의미/변경 이유가 같음 | 공통 장치 컨트롤러를 설정으로 조립. OvenHandle 전달자와 장치 이름 전용 클래스는 제거 |
| Cut 연출 | 현재는 Timeline+Track+Clip+Bridge+4패널 값 계층 | 단일 컷 Catalog·서비스 시계·VM·View로 충분. 패키지 삭제/다른 Timeline 자산 변경은 없음 |
| DialogueDriver / 임시 기름 수명 | Driver는 Cancel만 하고, Transient의 현재 생성자는 적 사망 기름뿐 | Core가 Cancel을 소유. 기름 생성 제거 후 세 Scope/수명 파일 제거. 기존 껍질 소유를 재사용 |
| 메뉴/작성 도구 | 실제 자산 생성·Play 보정·빌드에는 Editor 코드가 필요 | Prototype 보정 메뉴를 최초 작성 빌더에 흡수. Builder라는 이유로 모두 지우지 않음 |
| 인터페이스/버스/서비스 목록 | 실제 외부 실행·여러 소비자·범위 Dispose 경계를 표현 | IBrokenable/IState 및 미사용 이벤트/옵션 명령만 제거. 구현마다 새 인터페이스/팩토리는 추가하지 않음 |

현재 구조의 모든 부분을 필수라고 변호하지 않는다. 당시 수명 안전성을 얻기 위한 조립은 근거가 있지만 지금 요구에 비해 출력 교대·사라진 기름 수명·취소만 하는 Driver·두 Prompt·사후 보정 메뉴·단순 컷용 Timeline 어댑터는 비용을 늘린다. 반대로 물리/외부 실행/수명 경계까지 합치는 것은 상태와 해제를 다시 중복시킨다. 파일별 최종 판정은 [스크립트 명세](<스크립트 필요성 및 정리 명세.md>), 새 실제 배치 계약은 [프리팹 가이드](<미래 프리팹 연결 가이드.md>)를 따른다.

## 현재 확인의 한계

새 명세의 코드 구현/삭제·Play·Windows 빌드는 아직 수행하지 않았다. Unity 읽기 조회 당시 Title 씬 하나가 열려 있고 isDirty=false, Play 정지, 컴파일 실패/Console error0이었다. 이는 변경 전 상태이지 새 기능 통과가 아니다. 원본/소스/GUID/재귀 의존 검토 결과와 실제 기능 실행 증거를 분리한다. 기준점의 사용자 TestTitleBG prefab/메타 삭제 및 ProjectSettings 변경은 보존한다.

## 검토 중 추가로 관찰된 자산 변경

최초 기준점에는 없던 `Assets/_Scenes/Tech_SYM/Architecture/Session/PlayerRoot.prefab` 변경이 관찰됐다. 루트 활성값이 0→1이고 카메라 네 개의 로컬 위치가 달라졌다. 저장 주체는 확인하지 못했으며 이번 문서 작업에서 prefab 쓰기/저장 요청은 수행하지 않았다. 변경을 되돌리지 않고 `output/Tech_SYM/planning/system-v11-refactor-2026-10-06/concurrent-playerroot.json`과 대응 diff에 보존한다. 최초 native 조회의 비활성값은 현재 저장값이라고 재사용하지 않는다. 앞으로 만들 Actor의 비활성 생성 계약과 기존 자산의 관찰 상태도 구분한다. 이 변경은 새 리팩터링 구현 결과가 아니다.

후속 읽기에서는 루트 활성값이 다시 0으로 돌아갔고 네 카메라 위치 차이는 남아 있었다. 최종 관찰은 concurrent-playerroot-latest.json/diff에 따로 기록한다. 최초 기록을 현재 상태로 오인하거나 이 변화를 실행자의 수정으로 합치지 않는다.
