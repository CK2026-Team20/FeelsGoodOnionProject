## 구현/실행 검증 절차

`unity status --project-path <현재 체크아웃> --format json`, `unity pipeline list --format json` 뒤 실제 Editor 조회에 성공해야 한다. Play/build 전후 전체 loaded scene path/isDirty·active/setup/playModeStartScene·코드/보호 파일 hash를 기록한다. 미저장 작업은 임의 저장/폐기하지 않는다.

일회성 검증 소스와 결과는 `output/Tech_SYM/verification/system-v11-refactor-2026-10-06/<실행시각>/`에 둔다. Unity run_script의 dry_run 진단 후 실행하며 취소/finally 종료를 제공한다. 실제 InputSystem 입력, 물리 시간, Brain·애니메이션 완료, 재시도/두 판 종료를 관찰한다. 직접 서비스 요청/teleport를 전체 실제 입력 동선으로 보고하지 않는다. 결과 JSON에 케이스·관찰·실패·시각·명세/소스 hash가 실제 존재하는지 확인한다.

필요한 기능 검사 후 새 Windows 빌드는 `Cooked/Integration/Build Windows Player` / `Cooked.Integration.Editor.IntegrationBuildPipeline.BuildWindowsPlayer`를 사용한다. 설치의6씬 명시 목록을 사용하고 새 executable/hash·BuildReport·errors/warnings·설정 전후/자동 저장 원인을 기록한다. 이전 exe를 새 빌드로 사용하지 않는다. `.dryforge` 문서검사 PASS와 Editor/Build PASS를 혼합하지 않는다.

기능 케이스 Excel은 구현 완료 상태에 맞춰 기존 판정/서식을 보존한 새 기록으로 갱신한다. QA는 기존 Cooked! FunQA DOCX의 원본 양식을 유지하여 실제 해당 빌드 플레이 후 직접 평가한다. 팀 플레이/재미/아트 품질이 대기라면 그대로 남긴다. 이번 ready에서는 Excel의 기존 실제 결과와 FunQA를 새 성공으로 덮어쓰지 않는다.
