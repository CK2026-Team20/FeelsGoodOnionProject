## 목표·자료·제약·완료 기준

- 목표: 모호한 행동을 결정할 수 있도록 현재 동작, 대안, 장단점, 권장 이유와 변경 책임을 연결한다. 기존 동작을 새 명세로 간주하지 않는다.
- 자료: Desktop 지정 DOCX의 읽기 전용 저장본, HMS 플레이어·눈물·표현 코드, SYM 세션·장치·적·추격·UI 코드, 현재 SYM PlayerRoot/TearSkill 자산, 이전 준비 문서의 전수 조사.

- 완료 기준: 11개 범주의 각 질문에 대안 또는 이미 확정되어 제외된 이유를 제공하고, 근거·의존 관계·미실행 검증을 표시한다. 소스/기존 자산을 변경한 것으로 기록하지 않는다.

Q 제한은 이 행동의 최종 완료/취소와 정리가 끝난 뒤 해제한다. ③은 표현 중단과 행동 취소를 구분하고 행동이 아직 진행 중이면 Q를 수락하지 않는다. ①/②에서 껍질을 유지하려면 D01.05의 해제를 복귀 성공 시점까지 미루어야 한다. 이미 회수 시작에 제거했다면 취소 시 껍질 반환/재생성까지 명세해야 하므로 같은 규칙으로 혼합하지 않는다. 사망/Actor 폐기에서는 세 안 모두 미완료 요청과 껍질·표현을 정리한다. 즉시 복귀 A에서는 이미 상태가 변경됐으므로 이런 표현 종료가 복귀 상태를 되돌리지 않는다.

변경 책임: HMS Form/표현 출력의 허용 파일 변경 또는 담당자 계약이 필요하다. SYM은 동일 규칙을 복제하지 않고 Bridge에서 명령을 전달한다. 회수 전용 매니저·카메라 스크립트는 추가하지 않는다. 검증: 실패 Q는 형태/껍질/무게를 보존, 성공 Q는 한 번만 변경, 비행 중 이동·옵션·사망·누락 클립에서 잔여 표현/입력 제한이 없음. **모두 구현 후 실행 대상이며 미실행**이다.

| **D03.07 가림용 사물의 범위** | 벽/눈물을 막는 사물은 반드시 차단한다. 추가로 **A 모든 실제 Solid 사물·장치·발판과 다른 적 몸체도 차단**: 직접 닿는다는 의미가 명료하나 적끼리 방패가 된다. **B 환경의 Solid 사물·장치·발판만 차단, 다른 적은 가림에서 제외**: 범위 스킬이 적 전체에 잘 적용된다. **C 개별 차단 Collider 목록만 사용**: 배치가 유연하나 등록 누락 시 관통한다. 피격용이 아닌 탐지 Trigger/회수 VFX/자기 몸체는 가림용 Collider가 아니다. | **A**를 비교의 기본안으로 권장한다. 다른 적의 몸이 눈물의 장애물이어야 하는지는 아직 선택 사항이다. 어떤 안이든 실제 벽/사물이 차단 목록에서 빠지지 않는지 검수하고, 새 ProjectSettings 레이어를 임의 추가하지 않는다. |

**직접 피격의 권장 판정식(D02.03=A, D03.02=A, D03.03=A, D03.01=A 기준):** E 명령이 수락된 순간의 중심 O와 반경 R을 고정한다. 살아 있는 유효 대상의 Hurt Collider가 범위에 겹치면 후보로만 잡는다. 각 Collider의 실제 가까운 점 P가 `distance(O,P) ≤ R`인지 검사하고, O→P 구간을 가림/몸체 판정 대상으로 조회한다. 자기 PC·피격용이 아닌 탐지·표현 Collider를 제외한 **첫 유효 접촉이 그 적의 Hurt Collider이고 그 앞에 벽/사물이 없을 때만** 실제 피격으로 인정한다. 근접하여 O가 적 Hurt Collider 안에 있으면 0길이 Ray를 발사하지 않고 직접 몸체 겹침을 확인하는 예외를 둔다. 발동 원점 자체가 Solid 장애물 안에 있으면 정상적인 가림 조회가 성립한 것으로 간주하지 않는다. 각 적은 한 발동당 한 번만 처리한다. 범위 탐색용 Trigger나 VFX 접촉만으로 기절시키지 않는다.

**D03.03의 피격 Collider 연결 방식:** 현재 EnemyActor의 `body`는 접촉 피해용 **BoxCollider Trigger**다. 따라서 Trigger 전체를 무시하면 실제 적 몸체도 누락된다. 적 Body를 유효 Hurt Collider로 지정한 경우에는 Trigger라도 포함하고, 시야/상호작용/CP/표현용 탐지 Trigger만 제외해야 한다. 유효 Collider를 연결하는 대안은 **① EnemyActor가 이미 연결한 body인지 확인하는 판정 함수를 Bridge에서 HMS에 주입**, **② 기존 레이어+IStunnable 부모 탐색만으로 구분**, **③ 각 피격 Collider에 별도 전달 컴포넌트**다. **①을 권장**한다. 같은 책임의 새 스크립트를 늘리지 않고 기존 EnemyActor/Bridge의 공개 판정과 HMS의 작은 주입 계약으로 연결한다. ②는 같은 레이어의 탐지 Trigger를 몸체로 오인할 수 있어 배치 검수가 더 필요하고, ③은 물리 콜백이 따로 필요하지 않으면 전달자만 추가한다. 주입 함수는 Collider가 유효 몸체일 때만 원래 기절 소유자 IStunnable을 반환하며 다른 탐지 Collider는 거절한다. 후보 검사에서 거절된 Collider를 ‘이미 기절 처리한 적’으로 기록해 뒤의 실제 몸체 검사를 건너뛰지 않는다. HMS에서 SYM 구체 타입을 참조하지 않으며 Actor 해제 때 해당 주입도 해제한다. 이 공개 연결은 목표 계약이며 아직 구현되어 있지 않다.

중심까지의 거리가 3m보다 멀어도 몸 일부가 3m 안에 있고 그 부분에 직접 닿으면 D03.03=A에서는 적용할 수 있다. 반대로 구 범위에 포함되어도 선택한 직접 피격점이 벽/닫힌 서랍에 막히면 적용하지 않는다. 여러 점 방식을 선택하더라도 첫 실제 접촉이 반경 안의 대상 몸체여야 하며, 반경 밖 중심점이 보인다는 이유만으로 거리 조건을 우회하지 않는다. 가림 실패는 해당 적의 효과 없음이며 이미 수락된 눈물 발동 자체를 취소/환불하는 규칙과 분리한다.

API 근거: [Unity Physics.OverlapSphere](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Physics.OverlapSphere.html)는 구 안 또는 구와 접촉한 Collider를 반환하므로 중심 포함 규칙을 별도로 정하지 않으면 D03.03=A에 가깝다. [Unity Collider.ClosestPoint](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Collider.ClosestPoint.html)는 Collider의 실제 형상에 대한 월드 점을 구하므로 bounds 박스까지 닿은 것으로 오판하는 보정을 피할 수 있다. 비활성 Collider는 대상에서 먼저 제외한다. [Unity Physics.Raycast](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Physics.Raycast.html)는 발사 원점이 안에 있는 Collider를 검출하지 않으므로, 원점의 직접 몸체 겹침/장애물 내부를 Ray 하나만으로 처리하지 않는 것이 필요하다.

변경 책임: 보호 HMS TearSkill/Definition은 파일 허용 또는 담당자 작업이 필요하다. SYM Enemy가 기절 상태/남은 시간의 단일 소유자이며 눈물 효과 처리기가 별도 타이머를 보유하지 않는다. 검증: 벽/층/3m 경계, 다중 Collider, 남은 0.7초에서 재기절, 비용 부족/무대상/동시 사망, 옵션 정지 후 잔여 시간 보존. **미실행**.

## 6. 애니메이션

현재 HMS PlayerAnimationPlayback은 Dead/Knockback이 일회성 표현을 지우고, 낮은 우선순위 요청은 거절하며, 같은 우선순위의 새 요청은 처음부터 시작한다. 착지 표현 중 Idle이 아닌 상태가 되면 착지를 중단한다. | **D10.02 도착 대화 중 추격/안전** | **A 도착을 먼저 수락→추격 이동과 Capture 종료→메모/일반 대화 정리→최종 대화→완료→엔딩**. **B 추격을 진행한 채 대화**: 입력 제한 중 포획된다. **C 대화 동안만 월드 전체 정지**: 일반 대화의 월드 진행 예외가 생긴다. | **A**. 최종 대화 구역에 다른 데드존/피해원이 없도록 레벨 계약으로 보장하는 방식이 가장 단순하다. 다른 적이 들어올 수 있다면 ‘도착 수락 후 피해 금지’의 추가 승리 보호 정책을 선택해야 한다. 추격 종료만으로 모든 피해원이 사라진다고 가정하지 않는다. |
| **D10.03 추격 재시작 위치** | **A 시작선 이전의 안전 CP에서 실제 현재 위치 두 값을 캡처하고 성공 뒤 추격 시작**. **B 시작선 위치를 저장하고 리스폰 시 강제 추격 시작**: ‘다시 통과’ 규칙과 다르다. **C 시작선을 지난 위치를 저장하고 과거 Marker 위치로 복원**: 실제 저장 위치 지시와 충돌한다. | **A**. 도착한 프레임의 PC가 이미 시작선을 넘었다면 과거 Marker pose를 저장하지 않는다. 시작선 이전 CP 센서에서 먼저 캡처하고 그 승인된 두 값을 같은 추격 준비 흐름에서 사용한다. 직전 강제 갱신이 필요하면 시작 수락 센서를 선 이전에 배치한다. 저장 완료 후 선 통과→퇴로 차단의 순서를 배치/명령에서 보장한다. |
| **D10.04 같은 물리 스텝의 도착·포획** | **A 유효 포포 도착 우선**: 결승점에 닿았으면 성공을 보장한다. **B 포획 우선**: 추격 위험을 결승까지 유지한다. **C 거리/통과 시각을 보간해 더 빠른 쪽**: 정밀하지만 경로 교차/동률 규칙이 추가된다. **D 먼저 호출된 콜백 우선**: 순서가 재현되지 않을 수 있다. | **A**. 같은 Actor·같은 물리 스텝의 후보를 한 종료 수락 지점에서 비교한다. 이미 이전 스텝에 사망한 Actor의 늦은 도착은 인정하지 않는다. 우선순위는 사용자 선택이며 게임 규칙을 문서화해야 한다. |
| **D10.05 최종 대화 취소/누락** | **A 정상 완료·전체 Skip만 GameComplete, 제목 종료/Actor 소실은 취소**: 대화 결과를 정확히 구분한다. **B 대화 시작/취소도 완료**: 종료 조건이 A와 다르다. 데이터/화면 누락은 **명시 실패** vs **즉시 완료로 대체** 중 별도 정책이 필요하다. | 결과는 **A**. 필수 DialogCode/표현 연결은 빌드 전 검증하고 누락은 명시 실패·원인 기록을 권장한다. 프로덕션에서도 누락 시 엔딩을 보장하려면 대체 완료 정책을 별도 선택한다. 권한 있는 Skip은 Completed와 동등, Cancelled는 동등하지 않다. |

변경 책임: Stage는 도착/시작 센서의 의미를, Chase는 경로·진행·단일 시도의 종료를, Flow는 최종 대화 결과→엔딩 전이를 소유한다. 앞쪽 포획 전용 소스/별도 Escape 퍼즐/중복 완료 트리거는 새 경로로 참조 이관 후 삭제한다. 일반 Dialogue의 무관한 대화 완료가 엔딩을 시작하지 않도록 활성 Stage·DialogCode·요청을 확인한다. 검증: 시작선 건너뛰기·저장 실패·리스폰 후 재통과, 도착/포획 동일 스텝 및 이전 사망, 옵션·Skip·제목 종료·누락, 최종 대화 중 안전 보장. **미실행**.

## 선택과 구조·스크립트 필요성의 관계

현재 구성의 전체 206개 스크립트 조사와 32개 이관 후 삭제 후보는 [스크립트 필요성 및 정리 명세](<스크립트 필요성 및 정리 명세.md>), 실제 컴포넌트 연결은 [미래 프리팹 연결 가이드](<미래 프리팹 연결 가이드.md>)에 있다. 이 수치는 이번에 소스를 삭제했다는 뜻이 아니다. 해당 문서의 모호한 행동 전제는 이번 선택 결과에 맞춰 변경되어야 한다.

| 경계 | 현재 구조의 이유·문제 | 이번 선택에 따른 최소 구조와 필요성 |
|---|---|---|
| App / Core / Stage | 앱 입력·설정·전환, 한 판의 Actor/세션, 재로드 가능한 레벨의 수명이 다르다. 모든 것을 Bootstrap 하나에 넣으면 Stage 재시작 때 세션/옵션까지 지울 수 있다. 반대로 기능별로 씬/서비스를 계속 분리하면 조립 지점이 늘어난다. | 세 수명 경계는 유지하되 게임 흐름 조정과 물리/상태 소유를 혼합하지 않는다. 새 일반 기믹을 위해 별도 관리자·씬·인터페이스를 항상 만들지 않는다. Stage 재준비와 CP 두 값 복원은 기존 Runtime/ActorHost의 전환에서 수행한다. |
| 플레이어 / 카메라 | 현재 PlayerRoot의 CameraRig·출력 Camera는 Actor 생성/폐기와 함께 수명이 묶인다. HMS가 활성화 때 카메라 참조를 정하는 방식에 맞춘 조립 결과이며, Unity/Cinemachine이 플레이어 자식을 요구해서 생긴 구조가 아니다. App의 대기 출력과 Actor 출력의 전환은 출력/리스너 중복 관리 비용을 만든다. | 이미 선택한 앱 출력 하나+독립 리그를 사용한다. 플레이어에는 CameraAnchor만 둔다. Actor 생성/파괴마다 Follow/LookAt을 연결·해제하는 계약이 필요하고 세션 종료 때 이전 Transform을 참조하지 않아야 한다. 별도 ActorCameraRig 전달자/두 번째 출력 카메라를 유지할 이유가 없다. 보호 HMS의 재연결 계약 없이 SYM 복제 카메라 컨트롤러를 추가하지 않는다. |
| 빈 루트 / 몸체 / Visual | 기존 ActorBody에 Facade·Movement·Form·Capsule·Rigidbody가 같은 물리 몸체를 참조한다. 단순한 외형 계층 예시를 이유로 이를 서로 다른 자식에 분산하면 RequireComponent/충돌/발 위치 계약이 깨질 수 있다. | 빈 PlayerRoot는 수명/조립 진입, ActorBody는 물리 계약, VisualRoot의 NormalVisual/SmallVisual은 Renderer/Animator, VFX/SFX는 표현, CameraAnchor는 위치다. ActorBody에 논리와 물리 컴포넌트가 함께 필요한 예외는 연결 가이드에 명시한다. Visual에 제어 스크립트를 붙이지 않는다. |
| 폼 / 표현 / 회수 | 현재 Form이 물리 치수·무게·껍질을 소유하고 Playback/Output이 표현을 소유한다. 이 경계는 실제 상태 변경과 애니메이션 누락을 분리하는 이유가 있다. 회수 비행을 실제 물리 껍질과 연결하면 별도 미완료 상태가 생긴다. | 즉시 복귀라면 Form 명령 한 번에 상태를 완료하고 VFX만 재생한다. 표현 출력은 요청의 종료 결과만 보고한다. 같은 행동의 이전 회수 VFX를 새 수락/사망/세션 종료에서 정리해 표현 객체가 쌓이지 않게 한다. 회수/시간제한 전용 서비스·partial 분할은 필요 없다. |
| 이동 / 장치 / 센서 | 왕복 발판·압력 연동·트레이/서랍의 이동 구현이 각각 있으면 물리 작성자·운반·정지·막힘 규칙이 중복된다. 센서와 실제 이동 객체는 서로 다른 배치/수명 때문에 분리될 수 있다. | 공통 이동자는 하나, 장치는 목표/입력 수락과 자기 이동 상태, 압력판은 실제 접촉 판정만 소유한다. 고정 발판은 로직 없이 Collider/Visual만으로 충분하다. 독립 서랍 세 개에 이동자를 조합하는 것은 필요한 분리이며 전달만 하는 OvenHandle 같은 경로는 이관 후 제거 후보다. |
| 입력 / 피해 / UI | 현재 피해원별 간격·넉백, 메모/대화별 월드 정지, E/F 경로 분리가 중복 판정·잠금 해제 오류를 만들 수 있다. | 입력은 한 명령 라우팅, 피해는 한 수락/무적 규칙, UI는 기존 ViewModel 상태·Command 바인딩을 재사용한다. View가 직접 Facade·저장·Flow를 찾아 실행하지 않는다. ViewModel은 View를 참조하지 않는다. 한 화면의 순수 표현까지 모두 별도 스크립트로 나눌 필요는 없다. |
| 저장 / 해금 / 대화 | 현재 CP ID 기반 저장과 세션 해금이 혼재한다. 새 원본의 세계 저장을 구현하면 객체별 DTO/등록/복원 순서까지 추가되지만 직접 지시 범위를 벗어난다. | CP는 Position/Fragments 두 값과 캡처/검증만 필요하다. 해금·완료 대화는 선택한 세션 런타임 규칙이다. Stage 상태는 초기 배치로 만든다. 월드 Snapshot/Participant/Registry/SaveId/영구 진행 파일은 필요한 스크립트가 아니다. |

향후 프리팹에서는 Renderer/Animator·판정 Collider·InteractionAnchor·CameraAnchor가 어디에 연결되는지 명시하되, 단순한 위치 앵커마다 별도 스크립트를 만들지 않는다. 새 카메라 리그에는 Side/Quarter 가상 카메라와 기존 카메라 제어 계약만 연결하고 출력 Camera/Brain/Listener는 앱 쪽 하나에 둔다. 계층은 [미래 프리팹 연결 가이드](<미래 프리팹 연결 가이드.md>)를 따르며 선택이 바뀌면 해당 필드·연결·필요성도 함께 갱신한다.

## 현재 완료와 남은 선택

68개 결정 항목으로 11개 범주와 선행 미답변 3개를 비교했다. 사용자 확정 사항은 고정하고 나머지는 권장안/정리안으로 표시했다. 숫자 제안과 실제 코드값, 실제 실행과 정적 문서 검토를 구분했다. 새 코드를 구현/삭제하거나 기존 프리팹을 제거하지 않았다.

질문 대응·로컬 링크·문서 상태·코드/메타 482경로 보존·기존 실행 문서 보존 등 27개 정적 확인을 통과했다. 독립 검토에서 지연 복귀 누락/중단의 종료 선택과 사망 몸체 접촉의 현재 설명을 보완했고, 확인된 이웃 범위의 한 번 재검토에는 잔여 지적이 없었다. 사용자 선택이 확정됐다는 뜻은 아니다. 증거는 `output/Tech_SYM/planning/system-v11-ambiguities-2026-10-07/`의 `options-checks.json`, `question-coverage.json`, `independent-intent-review.json`이다.

우선 D01.01·D01.07·D07.02·D10.01~04를 선택하면 나머지 조건부 분기가 줄어든다. 모든 권장안을 한꺼번에 승인해야 하는 문서가 아니며, 항목 ID로 다른 선택이나 추가 조건을 제시할 수 있다. 눈물의 새 가림 규칙은 직접 답변으로 반영했고, 나머지 필요한 사용자 선택 후 기존 기능 명세/계획/인계·프리팹 가이드·테스트 기준을 최종화한다. 기존 `.dryforge` 실행 문서는 이번 선택 검토가 끝나기 전에 교체하지 않는다.
