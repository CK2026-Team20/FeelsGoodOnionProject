# 60·120·180개체 FPS와 전체 시나리오 개발 검증

## 목표·기준·제약·완료 판정
현재 BoidsTest의 12개 시나리오를 60·120·180개체로 순차 실행하고 이동 장애물 급락을 개선한다. 목표는 최소60FPS, 우선 목표144FPS다. 현재 소스, ScaleFPS/*.before, 사용자 미저장 씬 복사본 UserScene.before.unity가 기준이다. Inspector에서 사용자가 줄인 시나리오 배열1개, Volume_Arch100개체와 스폰 크기10을 보존한다. 재합류 기능은 보류하며 관찰만 수행한다. 보호 아트·원본 머테리얼·물리 주기·후보48개·예측1.2초·경로 폭은 임의로 축소하지 않는다.

36개 조합 실행과 성능 비교를 완료했다. 모든 조합에서 초기 개체 수 일치, 접촉·sweep·경로 이탈·볼륨 이탈·회피 계획 실패0, 타임아웃0이다. 이는 관찰 기간의 안전 계측 결과이지 전원 완주 또는 모든 기능 통과 판정이 아니다. **최소60FPS 유지 및144FPS 목표는 미달이다.** QA 제공용 테스트 케이스가 아닌 실제 개발 실행 기록이다.

## 환경과 측정 정의
- CPU AMD Ryzen5 5600X(6코어/12스레드), RTX3070Ti, 메모리32694MB.
- Unity Editor Play, D3D11, Game View1920×1080, VSync0, targetFrameRate=-1, 자동 tick0ms, Profiler 활성/Deep Profile 비활성. GPU Profiler는 비활성이므로 GPU 병목 확정 자료가 아니다.
- baseline/reuse-180은 비최대화 화면 조건. full-scene은 Game View 최대화 및 시험 카메라 외 같은 씬 Game Camera 비활성 조건이다. 이 환경 변경 효과를 코드 최적화 효과에 포함하지 않는다. 사용자 씬 자산의 카메라 설정을 저장한 변경이 아니다.
- 한 번에 하나의 군집만 활성화한 **12시나리오×3개체 수=36개 순차 측정**이다. 본편 전체 부하나12군집 동시 성능은 검증하지 않았다.
- 평균FPS=표본 프레임 수/실제 wall-clock 프레임 간격 합계. 1% low=가장 느린 ceil(표본 수×.01)개 프레임 간격 평균의 역수. 군집 계산시간의 역수를 FPS로 사용하지 않았다.
- FPS 표본은 게임 시간0.5~6초, 활성 개체 수가 목표와 같은 프레임이다. 첫 스폰과 개체 반환 이후를 제외한다. 접근 시간창은1.5~5.5초이며 조우 이벤트 기반 구간이 아니다. 안전·반환·연결 관찰은18게임초까지 수행한다.
- baseline180 Path는18프레임, wall 시간 합계15.12초다. 낮은 FPS에서 게임 시간이 느려져 실제5.5초 시험과 다르다. 적은 표본의1% low는 최악 한 프레임에 가깝다.
- 비이동 Path는180개체를 겹치지 않게 넣기 위해 시험 중에만 A를 뒤로30m, 스폰 중심을 군집 기준 z=-23m, 크기10×10×30m로 확장했다. 다른 시험 스폰은10³m다. **비이동 Path의 초기 FPS에는 장애물 도달 전 구간이 포함될 수 있어 이를 장애물 조우 중 FPS로 단정하지 않는다.**
- 에디터/도구 조회 오버헤드를 포함한 결과이며 반복실행 신뢰구간이나 Player 성능 보장은 아니다.

## 실제 병목과 변경
baseline 이동 Path180에서 선택 검사에 수집 wall 시간의 대부분을 썼고, 화면 한 프레임에 FixedUpdate가 최대17회 누적됐다. 후보별 미래 회전 궤적, 반복 경로 검사, native Transform 쌍별 조회, 개체별 Animation Graph Evaluate가 주요 수정 대상이었다.

1. 후보를 점수 상한 순서로 검사하고 최선 점수를 넘지 못하는 후보는 종료한다. 원래 후보 순서로 동점 처리한다.
2. 예측의 첫 이동은 실제 RotateTowards와 같게 검사한다. 이후 최대6tick을 한 번의 보수적 swept 검사로 묶는다. 각 시각의 실제 예측점과 같은 시각의 직선 보간점 사이 최대 오차를 몸 반경에 더하므로 곡선을 단순 직선으로 깎지 않는다. 이동 장애물 정지 시각 분할을 유지한다.
3. 짧은 회피 방향 재사용에도 매 tick 새 위치·속도·장애물로 전체 예측 궤적을 재검증한다. 무검사 프레임을 만드는 방식이 아니다.
4. 열린 직선 경로를 오차0.1mm 이하의 선분으로 축약하고 통로 반경에서 실제 축약 오차를 뺀다. 곡선의 일반 투영 방식은 유지한다.
5. 진단용 쌍별 거리는 개체별 위치를 한 번 읽고 제곱 거리 배열 연산으로 계산한다.
6. 풀당 하나의 애니메이션 그래프에서 개체별 독립 Idle 출력·위상을 평가한다. 원본 메시·Idle·Trail을 유지한다. 풀 Dispose가 직접 자신이 만든 그래프와 Batch를 해제하도록 수명 계약을 보완했다.
7. 내부 매우 빈번한 Arc/PathContains/Cast 마커는 BOIDS_DETAILED_PROFILING 조건으로 제한했다. Tick/Choose/Animation/PairDistances/Discovery의 상위 마커는 유지한다. 최종 pathNs=0은 계산 비용0이 아니라 상세 계측 비활성이다. 계측 오버헤드 감소도 전후 차이에 포함된다.

기존 화면 조건180개 이동 장애물의 평균FPS는 Path **1.19→54.80**, Volume **19.72→55.98**였다(baseline→reuse-180). 최대 FixedUpdate 누적은 Path17→2, Volume4→2였다. 부모/자식 ProfilerMarker는 중첩되어 합산하지 않는다.
그 후 화면 최대화·중복 카메라 제외를 적용한 full-scene은 Path62.68, Volume65.25다. 이를 모두 코드 변경만의 효과로 설명하지 않는다.

## 독립 리뷰와 가독성
독립 읽기 검토에서 묶음 궤적의 같은 시각 오차 반경, 첫 이동, 정지 시각 분할 및 후보 상한 선택을 검토했다. 공유 그래프의 해제를 부모 삭제에 의존하던 P2를 보완했다. 이후 풀/Idle 계약 실제 실행 결과는 pool-contracts.txt에 기록했다.
보이드 소스의 들여쓰기, 중괄호, 복합 조건, 긴 인수 및 초기화 구문의 줄바꿈을 정리했다. 포맷 변경은 전후 C# 토큰 일치를 검사해 로직 변경과 구분했다.

## 근거와 미완료 범위
원시 자료는 output/Tech_SYM/Boids/2026-11-13/ScaleFPS/ 아래다.
- baseline/results.json, frames.csv: 변경 전6개 이동 시험.
- candidate-order-180, straight-corridor-180, swept-batch-180, reuse-180: 단계별 중간 실행.
- full-scene/results.json, frames.csv:36개 최종 순차 측정.
- pool-contracts.txt: 풀 수명, 독립 Idle 출력·실제 Rig 변화, Trail, 재사용 계약.
- torus-supplement.json: 별도 구멍 통과·완주·애니메이션/풀 검사. 결과는 아래 추가 검증 절에 별도 기록한다.

현재 에디터에서180개체의 이동 계산을 멈춘 대조 관찰도 약74.5FPS였고, 실측 main-thread 표본에는 렌더 제출과 EditorLoop 비용이 남았다. 이 단일 대조로 GPU 한계나 실행 파일의 최대FPS를 확정하지 않는다. 최소60FPS 유지와144FPS 목표, Player 빌드/본편 동시 부하, 모든 경로 전원 완주 및 본대 재합류는 완료로 표시하지 않는다.

## 추가 실행 결과와 복원 확인

수명 보완 이후 별도 Torus 시험을 각 모드35게임초씩 실행했다. 실제 BoidTestSession 원본 결과 play-results-193714/193824/193934.json을 torus-supplement.json으로 묶었다. 임시 동적 보고 DTO가 빈 JSON으로 직렬화되어, 프로젝트에 컴파일된 BoidTestReport의 실제 원시 결과를 사용했다.

|---:|---:|---:|---|
| 60 | 60 / 60 | 12 | 접촉·관통·이탈·계획 실패0, Idle 진행·위상·풀 재사용 확인 |
| 120 | 120 / 120 | 27 | 접촉·관통·이탈·계획 실패0, Idle 진행·위상·풀 재사용 확인 |

경로는 세 개체 수 모두 전원 통과·완주했다. 볼륨은 기준 평면을 전원이 지났지만 구멍 통과는 일부다. 따라서 '전원 구멍 통과' 조건의 passed는 Volume 세 건 모두 false다. 별도 경로가 없는 볼륨의 회피는 구멍 선택을 강제하지 않는다. 이를 성공으로 덮어쓰거나 구멍 통과 유도 기능을 이번 범위에 추가하지 않았다.
개체 간 최저 중심 거리는 볼륨180에서 약0.0189m, 경로180에서 약0.2685m였다. 이는 몸 지름보다 작으므로 **이동 중 개체 간 겹침이 실제로 발생했다.** 최초 스폰 이격과 분리 조향만으로 지속적인 비관통을 보장하지 않는다. 장애물 무접촉과 개체 상호 겹침은 별도 판정이다.

최종 소스에서 CPU/Rendering Profiler만 남긴 별도180개 이동 재측정(final-cpu-only-180)은 Path 평균66.61/1% low33.28FPS, Volume 평균63.36/1% low34.72FPS였다. 양쪽 모두 안전 카운터0이며 최소60/목표144 미달 판정은 변하지 않았다. 계측 모듈이 달라 full-scene36개 결과를 이 수치로 교체하지 않았다.

풀/Idle 계약12건 실제 통과, 최종 컴파일 오류0, 포맷 토큰 일치 확인. 수명 보완은 독립 소스 재검토에서 종결됐다.36개 표는 수명 보완 직전 실행이고, 보완 이후에는 Torus6건·풀12검사·이동180 두 모드를 추가 실행했다.36개 전부를 보완 후 다시 실행했다고 표현하지 않는다.

Play와 Profiler 종료, Game View 크기·최대화와 Profiler 모듈·자동 tick16ms 복원. 현재 씬은 원래의 미저장 상태이며 원본 씬 파일을 저장하지 않았다. Inspector 시나리오1개, Volume_Arch100개체/스폰10³ 유지. 전후 미저장 씬 복사본 SHA-256이 동일하다: AF9FBC742CE36420B21D526E42B58A2F2894B345C2AF8E4FF3C07C50EA0ADFC6. Git 커밋·push 없음.
