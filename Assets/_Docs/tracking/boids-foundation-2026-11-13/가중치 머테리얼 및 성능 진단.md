# 보이드 가중치·머테리얼·Profiler 진단 — 2026-11-13

## 목표·참고·제약·완료 기준
사용자 요청은 세 군집 규칙의 가중치 설정, 몬스터 머테리얼 연결, 이웃 거리/런타임 장애물 검색 설명, 실제 Profiler 비교를 통한 회피 지연 원인 확인이다.
현재 BoidSettings/Group/Steering/ObstacleQuery/BezierPath와 현재 열린 BoidsTest를 기준으로 작업했다. _Art 원본, 기존 미커밋 변경, 씬 배치와 물리 설정을 보존했다. 회피 알고리즘 최적화·런타임 탐색 전환은 이번 변경에 포함하지 않는다.
완료 기준은 실제 설정 참조·계산 확인, 전용 프리팹의 머테리얼 연결 확인, 동일 조건 Profiler 비교 및 실행 판정/한계 기록이다.

## 반영
세 가중치는 이미 계산에 반영되어 있었다. 직렬화 필드와 수치를 유지하면서 Inspector 표시를 분리/정렬/응집 가중치로 명확히 수정했다. 현재 공유 BoidSettings.asset 값은 분리2, 정렬1, 응집0.5다. 비율 합100%가 아니며 각 항에 곱하는 값이다. 0이면 해당 항의 기여가 사라진다. 그룹별 다른 값이 필요하면 별도 BoidSettings 자산을 연결한다.
이웃 거리 Tooltip은 각 개체 중심의 이웃 탐색 반경이며 군집 기준점 최대 거리와 다름을 명시했다.
BoidAgent_Ghost.prefab의 monster_body SkinnedMeshRenderer에 Assets/_Art/Characters/Materials/monster_default.mat를 override로 연결했다. 원본 FBX·머테리얼·import는 수정하지 않았다. shader는 Universal Render Pipeline/RealToon/Version 5/Default/Default다.

## 측정 방법
현재 BoidsTest에서 Path_Arch(회피 발생0인 대조군), Path_ApproachingBox, Volume_ApproachingBox를 각12개체/18초/동일 시드로 순서대로 실행했다. 열린 경로는 도착 후 반환하므로 활성 업데이트 횟수가 다르다. 비교 값은 활성 군집 물리 업데이트 1회 기준이며 전체 구간의 평균 FPS로 비교하지 않았다.
Unity ProfilerMarker와 ProfilerRecorder로 Tick/Flock/Choose/Arc/StaticCast/MovingBox/PathContains, Main Thread를 수집했다. Deep Profile=false. 1차는 Profiler binary capture, 2차는 binary 저장을 끄고 동일 marker/recorder 측정을 반복했다. 엔진 fixedDeltaTime≈0.02, maximumDeltaTime≈0.3333을 변경하지 않았다. 단순 Stopwatch만으로 결론내리지 않았다.
원본 경로: output/Tech_SYM/Boids/2026-11-13/Profiler/baseline/capture.raw (약1.33GB), baseline/frames.csv 및 results.json, no-binary/frames.csv 및 results.json.
frames.csv는 marker 합계 nanoseconds와 호출 횟수를 프레임별 기록한다. GC counter 열만 bytes다. 수집기 자체의 작은 배열 할당과 Editor 실행/마커 오버헤드가 포함되므로 GC·빌드/GPU 성능으로 일반화하지 않는다. 단계 전환의 마지막 프레임 한 개가 이전 시나리오에 귀속될 수 있다(Volume 899 recorded ticks vs actual900). 실행 합격은 results.json을 따른다.

## 확인한 지연 원인
1. 후보 방향마다 전체 예측을 반복한다. 후보는 황금각48개+추가3개이며 실패 시 빠른 회전으로 재검사한다. 예측1.2초를 물리dt≈0.02로 쪼개 약60~61단계 검사한다. 안전한 평상시 방향도 이 전체 예측을 매 업데이트 수행한다.
2. 각 예측 단계에서 Path.Contains→Project가 주변 최대33개 선분을 다시 검색한다. 경로 이동 박스에서 이 반복 투영이 가장 큰 측정 하위 비용이다.
3. 정적 장애물 목록이 빈 이동 박스 시나리오도 StaticSafe가 전체 레이어(~0) SphereCastNonAlloc을 먼저 실행한 뒤 등록 목록으로 거른다. statics0/moving1을 실제 직렬화 값에서 확인했다. 이 경우 물리 질의 결과를 사용하지 않는 낭비가 있다.
4. 이동 박스 교차 검사도 각 단계마다 Transform/크기/예측 offset을 재조회한다. 여러 후보가 같은 물리 tick의 장애물 상태를 반복 조회한다.
5. 느린 물리 업데이트가 다음 화면 프레임에 누적된다. binary 끈 프레임2546에서 Tick17회, Choose204회, Arc4619회, StaticCast156935회, PathContains150965회. Tick 합643.7145ms, Main Thread659.7554ms. binary 저장 측정에서도 같은 연쇄 지연을 확인했다. 따라서 파일 저장만의 문제는 아니다. 이는 Profiler가 켜진 Editor 조건의 수치이며 사용자의 일반 실행 FPS라고 주장하지 않는다.
분리·정렬·응집 자체는 현재12개체에서 병목이 아니다. 더 큰 개체 수에서의 O(N²) 비용은 별도 검증 대상이다.

## 런타임 검색 설명과 개선 우선순위
현재도 SphereCast는 실제 최신 충돌체를 질의하지만 등록된 정적 목록에 없는 결과는 무시한다. 이동 미래 위치는 연결된 BoidMovingObstacle만 예측한다. Collider 목록은 고정 공간을 뜻하지 않는다.
런타임 장애물 발견은 가능하다. 장애물 LayerMask와 Trigger 제외로 주변 충돌체를 군집/개체별 가까운 후보로 추리고, 같은 tick의 후보 평가에서 재사용하는 방식이 적절하다. Rigidbody 속도 또는 위치 변화량을 이용해 이동을 추정할 수 있다. 미래 가속/정지는 별도 이동 계약이 없으면 알 수 없으므로 재계획과 예측 여유가 필요하다.
우선순위: 빈 정적 목록의 질의 제거 → 같은 tick 장애물 변환/속도 캐시 → 경로 투영 중복 감소 → 가까운 장애물 후보 재사용 → 회피 후보 검사량 조절. 미래 궤적 검사를 무작정 줄이면 충돌 회귀가 생길 수 있으므로 수정 후 같은 동작 검증이 필요하다. 물리 주기나 최대 시간만 줄여 증상을 숨기는 것은 근본 해결이 아니다.

## 검증과 잔여 범위
2회×3개 실제 Play 결과 모두 passed=true. 각 결과 contacts/sweptContacts/pathExits/boundaryExits/failedPlans=0, phaseBins12, animationAdvanced12, poolReused=true. 원래12개 전체 시험 재실행은 이번 변경에서 수행하지 않았다. 기존 개체 간 겹침 한계는 유지된다.
회피 로직은 측정 marker만 추가했으며 최적화 완료로 기록하지 않는다. 동적 자동 검색은 설계 설명이고 구현 완료가 아니다. Player 빌드/GPU/대규모 군집은 미검증.
