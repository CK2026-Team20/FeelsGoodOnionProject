# 스크립트 필요성 및 삭제 결과

최종 구조는 책임·상태 원본·생성/해제 수명·실제 호출/저장 참조를 기준으로 정리했다. 파일 수는 성능 지표가 아니다. 구체 MonoBehaviour만 Add Component, ScriptableObject는 Project 설정 자산이다. 일반 C#·ViewModel은 조립자가 생성/주입하고 값·정적 함수·인터페이스·추상 기반은 실행 코드가 사용한다. [제작 가이드](<씬 흐름과 수동 프리팹 제작 가이드.md>)에 실제 부착 위치와 필수 참조가 있다.

기존 AI prefab 파일은 삭제·재생성·Apply하지 않았다. 구형 컴포넌트 참조를 최소 이관해 Source 삭제를 가능하게 했고, 새 리소스 prefab 제작·교체는 사람이 맡는다. 실제 하트·Q/E·조각의 Graphic 소비가 남은 HudIconGraphic만 조건부 대기다.

## 서비스 로케이터와 조립자가 함께 있는 이유

현재 ServiceLocator는 Type별 등록·조회, 부모 범위 조회, 등록한 IDisposable의 역순 해제만 맡는다. AppComposition은 앱 서비스와 실물 Camera/Options/Fade/Audio를 만들고 연결한다. CoreComposition은 한 판 서비스 범위를 만들고 Actor/Stage/UI/추격/카메라를 연결한다. 조립자는 생성자 인자·Unity 참조·초기화 실패 시 회수를 알고, 로케이터는 어떤 게임 서비스를 만들지 몰라도 된다.

로케이터가 구체 서비스를 직접 생성하도록 바꾸면 서비스 추가 때마다 로케이터가 Scene/Audio/Player/GUI 구체 타입과 설정을 알아야 한다. 현재 방식은 로케이터를 범용 수명 관리자로 제한하고 생성 정책은 프로젝트 조립자 한 곳에 둔다. 모든 소비자가 매 프레임 Get을 호출하는 구조는 아니다. 조립자가 필요한 좁은 계약을 명시적으로 주입한다.

App/Core 조립자를 유지하는 이유는 서로 다른 앱·한 판 수명과 실제 생성/부분 초기화 실패 정리가 있기 때문이다. 각 서비스마다 별도 Composition/Factory를 추가하지 않는다. ApplicationService처럼 종료 호출 하나만 감싸던 객체와 GameUiRoot/GlobalUiRoot처럼 같은 수명에 참조만 재전달하던 중간 객체는 제거했다. CoreWorldBinding은 Actor와 Stage 교체 때 해제·재바인딩, 카메라 초기 준비, 추격 전 저장과 최종 대화 예약을 실제로 조정하므로 단순 중계와 다르다.

ServiceLocator.Register는 해당 IDisposable의 해제 소유권을 범위에 넘긴다. 같은 인스턴스를 여러 계약으로 등록해도 한 번만 해제하고 부모가 소유한 서비스를 자식 범위가 다시 소유하지 못한다. Dispose 중 다른 항목도 끝까지 정리하고 오류는 집계한다. 이 방어는 삭제 수량을 늘리기 위해 제거할 수 없다.

## 주요 구현 방법의 선택 이유

- 위치는 실제 Transform을 연결한다. 편집 시 사람이 눈으로 배치하고 기존 좌표를 외울 필요가 없으며, 이동 Body 아래 목표가 따라가는 실수는 검증 단계에서 거절한다. 속도·시간·각도는 기능 수치여서 숫자를 유지한다.
- CP는 세 값을 먼저 검증한 불변 Snapshot으로 한 번에 교체한다. 일부 값만 저장되는 상태와 저장 실패 후 기존 정상값 손실을 막는다. 첫 저장 전 기본 진입은 별도 의미이며 Marker 좌표를 실제 접촉 위치 대신 저장하지 않는다.
- 생성 발판은 실제 Collider 기하로 세로 침투를 계산한다. 보기 좋게 메시만 위로 보내면 Collider가 여전히 끼기 때문에 ActorBody를 위로 분리하고 사망 표현 완료와 흐름을 연결한다. 정확히1/4는 사망이다. 껍질은 플레이어와 다른 물리 객체라 별도로 분리한다.
- 눈물은 Root를 Tween한다. Trigger를 가진 Sensor까지 같은 배치 단위를 따라가므로 메시와 수집 판정 위치가 다르지 않다. Render에는 추가 물리 writer를 두지 않는다.
- 최종 POPO 회차는 일반 완료 장부 삭제로 해결하지 않는다. 사용자 선택 2번 예외만 허용하고 Actor 세대·Round·대화 Session·선택 객체를 캡처한다. 콜백이 늦게 도착했을 때 다른 판/Actor/대화의 엔딩을 열지 않게 한다.
- HMS 이동의 실제 Inspector 접지각을 읽는다. 공개 readonly getter 한 개로 기존 값에 접근하며 SYM에 45도 같은 별도 접지 규칙을 추가하지 않는다. 보호 기본값·범위·접지 동작은 바꾸지 않는다.
- Animator/Renderer를 실제 Body 아래에 둔다. 외형 회전과 물리 이동을 구분하면서 피격·발판 분리에서 CameraAnchor도 현재 몸체를 따라가게 한다. 기존 HMS 동거 규칙은 예외로 명세하고 편의상 분리하지 않는다.
- 새로운 스테이지 전환·네트워크·저장 디스크·범용 WorldSave·레벨 객체 ID 체계를 추가하지 않는다. 사용자 목표는 Prototype에서 한 게임 흐름1회이며 향후 등록 Stage 독립 진입 경계만 보존한다.

현재 부족한 것은 코드가 아니라 실제 사람이 연결할 하트·미연결 애니메이션/아트 리소스와 사람 Play 결과다. 최종 코드 분석에서 추가 기능 누락이 발견되면 구체 소스·조건과 함께 수정하거나 findings에 따로 기록해야 하며, 기존 실행 결과를 새 구현의 통과로 재사용하지 않는다.


## 조건부 삭제와 남은 작업

HudIconGraphic은 하트 Sprite + Image3개 연결만으로 소비0이 되지 않는다. 기존 Q/E·조각 아이콘까지 새 표시로 바꾸고 Native12개/raw GUID6곳의 저장 참조를 모두 이관해야 한다. 그때 HudView의 숨은 hearts fallback과 Configure 잔재, HudIconGraphic Source/meta를 제거하고 비 Play import/compile을 다시 실행한다. 에이전트가 placeholder Sprite나 새 prefab을 만들어 조건을 충족한 것으로 처리하지 않는다.

HMS41개·공용 Interfaces5개는 보호 원본이다. 기능이 불필요해 보여도 삭제 권한으로 바꾸지 않는다. 통합 Player에는 HMS의 Temporary/Test 입력 컴포넌트를 추가하지 않는다. 세 파일의 명시된 최소 변경과 소유 prefab 설정은 [HMS 기록](<이전 Tech_HMS 변경 기록.md>)을 따른다. 기존 HMS MovingPlatform과 SYM Motion은 회전/Tween/압력/지지 계약이 달라 이름만으로 대체하지 않으며 동일 Body에 두 writer를 함께 붙이지 않는다.
