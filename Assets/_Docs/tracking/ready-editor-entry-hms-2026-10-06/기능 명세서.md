# 활성 씬 Play 및 HMS 기능 조립 명세

2026-10-06. 승인 검토용 명세다. 제품 코드·씬·프리팹 구현은 아직 시작하지 않았다. 적용 기준은 현재 사용자의 직접 지시, `Assets/_Docs/planning-index.md`의 지정 기획, HMS 기준 씬의 실제 컴포넌트 계약이다.

## 목표와 이유

편집 중인 씬을 Play했을 때 지정 통합 씬은 필요한 Bootstrap/Core를 준비한 뒤 선택한 스테이지로 진입하고, 그 밖의 씬은 그 씬에서 직접 시작한다. 프로그래머가 대상 경로와 도착 스테이지를 코드에서 안전하게 바꾸는 방법을 문서화한다.

HMS가 구현한 기능을 SYM 소유 객체의 역할에 맞게 조립하고 누락된 참조와 중복 책임을 바로잡는다. 게임플레이 카메라는 `Assets/_Scenes/Tech_HMS/01_PlayerMovementTest.unity`의 HMS 및 Cinemachine 구성으로 연결한다. 기능 파일이 존재한다는 사실만으로 설치 완료로 취급하지 않는다.

“참조”는 보호 원본의 기능을 소유 객체에 조립하는 것도 포함한다. 타인 원본을 수정하지 않는 권한 경계와 컴포넌트를 사용할 수 있는 조립 권한을 명확히 구분한다.

## 변경 요구사항

### R1. 실제 활성 씬을 기준으로 Play 진입

Play 요청 직전 실제 편집 활성 씬의 **전체 자산 경로**를 원본 진입 경로로 사용한다. 아래 여섯 경로만 Bootstrap 강제 대상이다. 기준 디렉터리는 `Assets/_Scenes/Tech_SYM/Architecture/`다.

| 편집 활성 씬 | 처음 여는 씬 | 준비 후 도착 |
|---|---|---|
| `01_Bootstrapper.unity` | Bootstrapper | Title |
| `02_Title.unity` | Bootstrapper | Title |
| `03_InGameCore.unity` | Bootstrapper | Core + `Prototype/1_Stage.unity` |
| `Prototype/1_Stage.unity` | Bootstrapper | Core + 같은 Stage, ID `1_Stage` |
| `Stages/03_2_Stage.unity` | Bootstrapper | Core + 같은 Stage, ID `03_2_Stage` |
| `Stages/03_3_Stage.unity` | Bootstrapper | Core + 같은 Stage, ID `03_3_Stage` |

Stage 직접 진입은 기존 직접 진입 체크포인트·조각·해금 설정을 사용하고 오프닝을 생략한다. Bootstrap/Title의 새 게임 흐름은 기존 Title → 오프닝 → 첫 Stage 흐름을 유지한다. Core에는 선택한 Stage가 없으므로 설치 목록의 첫 Stage를 사용한다. Stage2/3를 첫 Stage로 바꾸는 공통 fallback은 금지한다.

목록 밖의 씬은 실제 활성 씬에서 직접 Play한다. 기존 `Tech_SYM/01_BootStrapper`, `Tech_SYM/02_Title`, `Architecture/Stages/03_1_Stage`, HMS 기준 씬과 개별 기능 씬은 목록 밖이다. 같은 파일명·접두사·부분 문자열로 대상을 넓히지 않는다. 아직 저장하지 않아 path가 빈 씬도 비대상이며 저장을 강제하지 않는다.

시작 설정에 Bootstrap이나 다른 씬이 이미 남아 있어도 비대상의 해당 Play 요청 동안 `playModeStartScene`은 null이어야 한다. 이는 편집 활성 씬의 독립 Play를 보장하기 위한 임시 설정이다. Play 종료·시작 취소·실패 시 원래 시작 설정과 Enter Play Mode 설정을 되돌리되, 그 사이 사용자나 다른 도구가 변경하여 현재 값이 자신의 소유 값과 달라졌다면 그 값을 덮어쓰지 않는다. 활성 씬 선택의 정책에 다시 필요한 임시 설정은 새로운 원래 값과 소유 값을 기록해 적용한다.

일회성 진입 정보는 `SourcePath`, `DirectGame`, `StageId`, pending 여부를 하나의 유효한 route로 취급한다. Title route는 `DirectGame=false, StageId=null`, Stage/Core route는 `DirectGame=true, StageId=위 표의 ID`다. 이전 Stage route를 비대상 또는 Title 진입에 재사용하지 않는다. route는 Bootstrap 소비 후 또는 Stop/취소/진입 실패 시 제거한다. Domain Reload 유무에 따른 중복 소비·잔존을 막고, 통합 씬의 초기화에 필요한 Scene Reload는 기존 Hook의 임시 보장과 복원을 유지한다.

대상 경로와 `ArchitectureInstallation`의 설치 경로·Stage 순서가 불일치하거나 필수 자산이 없으면 문맥이 있는 오류로 해당 통합 진입을 중단하고 임시 설정을 정리한다. 비대상 씬의 직접 Play는 설치 자산이 없어도 가능해야 한다. 편집 씬을 자동 저장·폐기하지 않는다.

### R2. 프로그래머가 수정할 경로와 계약 설명

`BootstrapEntryRoute.IsTarget/TryResolve`의 정확한 경로 목록 및 도착 매핑, `BootstrapPlayModeHook`의 시작 씬 설정·복원, 설치 자산의 Stage Paths, 각 Stage의 StageId/체크포인트, `IntegrationEntrySettings`의 직접 진입 데이터를 함께 설명한다. 새 Stage N 등록 시 현재의 세 Stage 개수·순서 대조, 기대 검증과 명시적 빌드 목록을 함께 갱신하는 예를 제공한다.

시작 씬을 Bootstrap으로 고정하는 설정과 Bootstrap 이후의 도착 Stage를 고정하는 설정이 서로 다른 책임임을 명시한다. 문서의 코드 예는 실제 수정 지점과 일치해야 하며, 예제 대입만으로 임시 설정의 복원과 오류 처리가 완성된다고 설명하지 않는다.

### R3. 역할별 HMS 기능 설치 및 리팩터링

현재 감사 모집단은 `Assets/_Scenes`의 프로젝트 씬 16개와 저장 `.prefab` 65개다. 설치 플러그인의 예제 씬은 제외한다. 각 파일의 객체·상속 프리팹·인스턴스 override·런타임 생성 경로를 함께 확인한다. 구현 완료 때 자산이 추가되면 모집단도 갱신한다. 보호 원본은 조사와 결함 인계 대상이며 아래 허용 범위 안의 소유 배치만 수정한다.

| 기능 역할 | 설치·연결 기준 |
|---|---|
| 통합 Actor | HMS Facade·CharacterMovement·InputReader·SkillController·FormController·MovementModeController·VisualController·SlipperyEffect 및 기존 애니메이션 소비 연결. 원본 물리 계약 보존 |
| 입력 | 통합 Actor에는 InputReader 한 개와 GameplayInputRouter 한 개. HMS PlayerController/임시 테스트 입력을 추가하지 않음. 독립 기능 씬의 기존 입력 경로는 그 씬의 역할에 맞게 유지 |
| 폼·스킬 | 세 skill definition, visualRoot, debrisPrefab 등의 필수 참조가 실제 역할에 맞는 자산을 가리킴. 순수 Model/FSM/Skill/Playback/Definition 타입은 기존 생성·데이터 계약으로 사용 |
| 기름·적 | OilSurface와 플레이어 SlipperyEffect의 수신, EnemyStunVisual·StunEffectOrbit의 기절/해제 연결. 이미 정상인 구조를 재설치하지 않고 기능 확인 |
| 껍질·발판 | Passenger·PlatformRigidbodyMovement 및 Rigidbody/Collider 소유 관계를 보존하며 탑승·압력판·반환 수명 확인 |
| Stage | Core의 SessionActorHost가 플레이어를 생성하는 Stage에는 중복 플레이어를 저장하지 않음. 실제 생성 인스턴스에서 연결 판정 |

SYM `Architecture/Session/PlayerRoot.prefab`의 누락된 HMS 이동 모드·외형 담당을 설치한다. SYM `ActorFacingPresentation`과 HMS `PlayerVisualController`가 같은 외형 Transform을 동시에 갱신하지 않도록 책임을 정리한다. 이동 규칙의 권위는 HMS이며 SYM bridge에 같은 속도·축 규칙을 다시 구현하지 않는다.

SYM `Prefabs/MultiFuncPlatforms.prefab/Player_HMS`와 `01_BrokenablePlatformTest.unity/Player`에 확인된 세 skill definition 및 form visualRoot/debrisPrefab 누락을 수정한다. 상속 씬의 override로 다른 잘못된 연결이 남아 있지 않아야 한다. 용도가 없는 일반 객체에 모든 HMS 컴포넌트를 일괄 추가하지 않는다.

SYM `02_MultiFuncPlatformTest.unity/Main Camera`, `03_InGame.unity/Camera`의 Missing Script는 원래 GUID·클래스·역할을 조사한 뒤 필요한 소유 카메라 구성에서 해결한다. 삭제만으로 정상이라고 판정하지 않는다. HMS 기준 씬의 `PlatformManager` Missing Script는 보호 원본의 기존 결함으로 별도 기록·인계하고 직접 수정하지 않는다.

### R4. HMS Cinemachine 카메라 구성

SYM 소유 게임플레이 배치에는 출력 Camera+CinemachineBrain+HMS PlayerCameraController와 서로 다른 네 `CinemachineCamera`를 연결한다. 네 모드는 HMS `Side=0`, `Quarter=1`, `Back=2`, `BackFixed=3` 계약을 사용한다. 선택/대기 우선순위 기본값은 20/10이다. 출력 Camera와 Brain은 Cinemachine 화면을 렌더링하는 필수 구성이다.

기준 씬의 SideCam·QuaterCam·BackCam·BackFixedCam에 대응하며, CinemachineFollow와 Back의 RotationComposer, Follow/LookAt target, binding mode, damping, lens를 역할에 맞게 옮긴다. Back은 외형 방향을 따라가고 BackFixed는 월드 방향을 유지한다. 기준 FollowOffset 기본값은 Side `(0,2.5,-14.02)`, Quarter `(0,12.2,-6.05)`, Back `(0,3,-6)`, BackFixed `(0,2,-6)`다. 소유 배치에서 Inspector 조정 가능한 값으로 둔다.

기존 Stage의 `Side → Corridor → Quarter → Corridor → Quarter` 동선과 트리거/체크포인트를 보존한다. `CameraMovementMode.Side→HMS Side`, `Quarter→Quarter`, 월드 Z 이동인 `Corridor→BackFixed`, `Legacy→AllowDepth에 따라 Side/Quarter`로 연결한다. HMS Back 구성은 설치하되 이번 작업으로 새 Back 트리거나 레벨 동선을 추가하지 않는다.

전환은 Cinemachine의 실제 카메라 블렌드가 담당하고 기존 SYM의 출력 카메라 Transform 직접 갱신은 제거한다. 전환 동안 해당 담당의 gameplay 차단을 유지하고 입력을 비운다. 기존 Side/Corridor 평면 정렬은 물리 Pose와 함께 보존한다. 블렌드와 정렬 완료 후 HMS의 실제 이동 모드를 확정하여 이동축을 적용하고 자기 차단만 해제한다. 별도의 타이머가 먼저 끝났다는 이유로 아직 블렌드 중인 입력을 열지 않는다. 같은 구간의 반복 접촉은 중복 전환·구독·차단을 만들지 않는다. 다른 구간이 이어지면 이전 전환을 정리하고 최신 요청으로 전환한다.

초기 Stage/체크포인트 진입은 올바른 모드·카메라·이동축이 준비된 후에 게임플레이를 표시하고 입력을 연다. 시작 시의 잘못된 Side 화면이나 이전 Actor의 카메라가 사용자에게 노출되지 않아야 한다. 옵션 정지 중에는 블렌드와 정렬도 일관되게 정지하고 닫은 후 이어진다. 재시도·사망·세션 종료·비활성화·실패는 진행 중 전환과 자기 차단·구독을 정리한다.

HMS `PlayerCameraController`는 첫 Awake 전에 유효한 ModeController와 서로 다른 네 카메라 참조를 가지고 있어야 한다. protected private 필드를 런타임 reflection으로 채우거나 보호 코드를 수정하지 않는다. 비활성 소유 프리팹의 내부 참조 조립 등 실제 계약을 만족하는 방식으로 구성한다. `PlayerMovementModeController.IsInitialized`가 참인 후 `TrySetMode` 결과를 확인한다. false를 성공으로 처리하지 않는다.

재시도마다 새 Actor에 카메라의 이동 모드 담당·Follow/LookAt·월드 UI 카메라가 함께 연결되고 이전 Actor 참조는 해제된다. 지속 Core와 Actor 수명을 구분한다. 독립 SYM 게임플레이 씬도 자기 플레이어와 같은 HMS 카메라 구성을 사용한다. 기존 `Stages/03_1_Stage`는 필요한 조립만 수정하고 레벨 전체를 재생성하지 않는다. Bootstrap/Title의 화면 출력·연출용 Camera와 게임플레이가 없는 Sample/Art 씬은 용도가 달라 게임플레이 카메라 설치 누락으로 판정하지 않는다.

모드별 속도 기본값은 5m/s, 일반 카메라 전환 시간 기본값은 약 0.6초다. 두 값은 최신 지정 기획에 따른 **Inspector 조정 가능 기본값**이다. 기준 씬의 쿼터 속도 3m/s·블렌드 0.5초와 구분한다. 애니메이션 모델·클립 제작이나 _Art 원본 교체는 이 범위에 포함하지 않는다.

### R5. 참조 권한의 모호성 제거

루트 AGENTS/CLAUDE와 `security.md`, `standards.md`, `contracts.md`, 관련 SYM 지역 지침에 다음 의미를 일관되게 적용한다.

> 읽기·참조 허용은 타 작업자의 원본 코드·자산을 확인하고, 공개 API와 이벤트를 사용하며, 허용된 자기 소유 씬·프리팹·오브젝트에 그 기능의 컴포넌트를 추가·설정·연결하는 것을 포함한다. 자기 소유 배치의 prefab instance override는 해당 배치에 저장할 수 있다. 타 작업자의 코드·씬·프리팹·.meta·import 설정의 직접 수정, 보호 원본에 prefab Apply, 원본 이동·삭제·GUID 변경은 별도의 명시적 파일 허가 없이는 금지한다. _Art·공용 자산도 같은 원본 보호 원칙을 적용한다.

같은 규칙을 “참조는 읽기만 가능하므로 기능 조립도 불가”로 다시 축소하지 않는다. 반대로 조립 허용을 보호 원본 수정의 포괄 허가로 확대하지 않는다.

### R6. 보존 및 실제 검증

수정 전 사용자의 기존 변경을 기록하고 보존한다. 현재 작업은 Tech_SYM 코드·씬·프리팹·소유 설정 및 승인된 프로젝트 Markdown 범위다. Tech_HMS/다른 작업자 원본, 공유 Interfaces/PlayerCharacter, _Art, Packages, ProjectSettings, 그 원본의 .meta는 직접 수정하지 않는다. SYM 소유 및 문서 자산의 필요한 metadata만 Unity GUID 계약을 보존해 처리한다. Git stage/commit/push/PR/merge는 이 명세의 승인이 아니다.

컴파일 오류, 대상 소유 객체의 Missing Script·필수 참조 누락, 중복 입력/상태/외형 갱신, 초기화 이전 모드 적용, 이전 Actor 카메라 잔존을 실행 증거로 검증한다. Play 전 scene setup·active·startScene·dirty·Enter Play Mode 설정을 기록한다. dirty 작업이 있으면 자동 저장·폐기 없이 해당 상태를 보존하고 상태 변경 검증을 보류한다. 실행 후 setup과 설정을 자신의 임시 변경 범위에서 복원한다. 소유 배치의 의도한 변경은 실제 저장 후 isDirty=false와 디스크 diff를 확인한다.

최소 기능 시나리오는 여섯 통합 진입, 대표 비대상 네 진입 및 빈 path 정책, Bootstrap 잔존/외부 startScene/취소/Reload 조합, 세 Stage 카메라·이동·F/E/Q·기름·폼·껍질·기절·재시도·옵션 정지·두 판 반복이다. 각 동작에 해당하는 실제 객체와 프리팹을 추적한다. API 검사나 구조 스캔만으로 InputSystem 동선 또는 사용자 빌드 Play 통과를 기록하지 않는다.

현재 Windows 명시적 여섯 씬 빌드 절차를 사용하고 ProjectSettings의 기존 변경 위험을 별도 검사한다. 빌드 성공과 실행 파일의 실제 플레이 검증은 따로 기록한다. 기능 케이스 엑셀은 프로그래머가 갱신하고 QA 평가 원본 양식의 FunQA DOCX 한 개를 보존한다. 팀이 실행할 실제 빌드 케이스와 자동 검증 결과를 혼합하지 않는다. 세부 실행 증거와 미실행/차단 사유는 `테스트 및 검증 항목.md`에 기록한다.

## 사용하는 경계

SYM Foundation은 진입 경로·일회성 route·설정 복원을, SessionActorHost는 Actor 생성/교체/제거를, CoreWorldBinding은 Stage/Actor/카메라/UI 연결을, LevelCameraService는 구간 요청·정렬·차단 수명을 소유한다. HMS는 PlayerFacade 상태, MovementModeController 모드·이동 설정, VisualController 외형 표현, PlayerCameraController 모드별 우선순위를 소유하고 CinemachineBrain이 출력 블렌드를 수행한다.

실행은 HMS 공개 `TrySetMode`, `CurrentMode`, `IsInitialized`, `ModeChanged` 및 기존 Facade 계약을 사용한다. 소유 프리팹 편집 시 Unity Editor 직렬화 API로 필수 연결을 작성한다. 실제 카메라 블렌드·priority·target 제어는 설치된 Cinemachine 공개 API로 수행한다. 현재 shared 인터페이스를 무단 변경하지 않고 필요한 소비 어댑터는 SYM 안에 둔다.

## 완료 판정

R1~R6의 파일 변경과 검증 증거가 모두 연결되어야 구현/자동 검증 완료로 판정한다. 보호 원본 결함은 별도 소유자 인계로 표시하며 “모든 프로젝트 자산 결함 0”으로 과장하지 않는다. 현재 ready 감사의 16씬/65프리팹 구조 확인과 원본 해시 보존은 이미 수행한 조사이고, 앞으로 수행할 게임 기능·수정 후 컴파일·빌드 검증과 분리한다.
