## 책임과 연결 검토

HMS가 모드·속도·축·외형·Facade 상태를 소유하며 Brain이 출력 Transform을 쓴다. SYM은 구간 요청·물리 평면 정렬·자기 input lease와 세션 수명을 조정한다. Preview 선택은 진행 요청이며 두 번째 권위 모드가 아니다. 같은 zone 억제와 다른 실제 trigger의 최신 요청을 각각 검증했다.

비활성 Actor에서 Mode/Visual·HMS CameraController·네 서로 다른 카메라·Follow/LookAt을 먼저 직렬화한다. Start의 IsInitialized 이후 initial mode/Brain 선택이 끝난 뒤 표시한다. retry에서 borrowed UI/trigger/camera 연결을 끊고 새 ActorReady에 재연결한다. 한 통합 Reader/router를 유지하며 독립3씬에는 한 Reader/HMS Controller만 둔다. ViewModel 상태 구독을 Actor마다 중복 생성하지 않는다.

독립 Primitive renderer는 VisualRoot/NormalVisual에, SmallVisual은 기존 capsule/작은 폼 규격에 맞게 배치했다. Visual 하위 물리는 없으며 기존 Facade·Rigidbody·Collider·센서의 공존 계약을 보존했다. InteractionSystem 원본의 player/prompt/camera3슬롯은 배치용 계약이며 실제 InGame override는 연결됐다.

소유 옛 두 camera Missing Script는 GUID/역할을 확인해 제거하고 실제 HMS 출력으로 소비 참조를 교체했다. MultiFunc의 옛 Main Camera 객체는 inactive, Camera/AudioListener도 disabled로 보존되어 경쟁 출력이 없다. LayoutOverview 역시 비활성 배치 참조다. HMS PlatformManager의 보호 Missing1은 소유자 인계다.

## 확인한 진입 문제

`BootstrapPlayModeHook`은 Edit Mode에서 대상 씬을 감지하면 Bootstrap을 `playModeStartScene`에 설정한다. 조사 시작 시 활성 씬은 `Architecture/Prototype/1_Stage.unity`였고 startScene, `PreviousStart`, `OwnedStart`가 모두 `Architecture/01_Bootstrapper.unity`였다.

비대상 씬에서 `RestoreTemporarySettings()`가 실행되어도 이전 값이 Bootstrap이면 다시 Bootstrap을 설정한다. 순수 경로 매핑은 Stage2·Stage3를 각자의 ID로 반환하지만, 시작 씬의 이전 값 자체가 고정된 경우 비대상 독립 Play가 보장되지 않는다. 이 코드 경로와 실제 설정은 확인했다. 아직 비대상 씬에서 Play를 새로 시작하여 증상을 재현하거나 수정 후 검증하지는 않았다.

## 기준 씬의 카메라 설정

Main Camera에는 Camera·CinemachineBrain·PlayerCameraController가 있다. CameraController의 movementModeController는 Player에 연결되고, side/quarter/back/backFixed는 서로 다른 SideCam·QuaterCam·BackCam·BackFixedCam에 연결된다. 선택/대기 우선순위는 20/10이다.

각 카메라는 CinemachineCamera와 CinemachineFollow를 사용한다. BackCam에는 RotationComposer도 있다. FollowOffset은 Side `(0, 2.5, -14.02)`, Quarter `(0, 12.2, -6.05)`, Back `(0, 3, -6)`, BackFixed `(0, 2, -6)`다. 원본의 실제 target·binding·damping·lens와 prefab override는 원시 감사 보고서에 보존했다. Back은 외형 방향을 따르고 BackFixed는 월드 방향을 고정하므로 같은 연결로 합치지 않는다.

기준 씬의 쿼터 속도 3m/s·Brain blend 0.5초는 확정 시스템 기획의 모든 시점 5m/s·약 0.6초와 다르다. 변경 명세의 기본값은 최신 기획을 유지하며 Inspector에서 조정 가능하게 둔다. 이 수치 선택 질문에 별도 답변이 도착하면 승인 전 명세에 반영한다.

## 수명과 리팩터링 확인 사항

- HMS MovementModeController는 `Start`가 완료되기 전 `TrySetMode`를 거절한다. Actor 생성 직후의 초기 체크포인트 모드 적용을 성공으로 간주하지 않도록 조립 순서를 검증한다.
- HMS CameraController의 필수 참조는 `Awake` 이전에 준비되어야 한다. 보호 코드의 private 필드를 런타임 reflection으로 쓰는 연결은 채택하지 않는다.
- 현재 LevelCameraService는 이동축과 일반 Camera Transform을 직접 갱신한다. Cinemachine 적용 후 모드 상태의 권위는 HMS가 갖고, SYM은 트리거·정렬·전환 중 차단과 해제 수명만 맡는다.
- 재시도마다 Actor가 교체되므로 Follow/LookAt·카메라의 mode controller·월드 UI 카메라가 이전 Actor를 계속 가리키지 않아야 한다. 자기 구독과 차단만 해제한다.
- 통합 Actor에 PlayerController·CheckInteract·TestPlayerFunc·PlayerSkillHUD·TestPlayerMovementMode를 복제하면 입력 중복이 생길 수 있다. 독립 씬의 기존 입력 경로와 통합 GameplayInputRouter를 구분한다.
- 모든 HMS C# 파일은 컴포넌트가 아니다. Model·FSM·Skill·Playback·Definition 등의 타입은 기존 생성·설정 계약으로 사용하며 모든 오브젝트에 붙이지 않는다.

## 이번 실행 증거와 한계

16개 프로젝트 씬과 65개 저장 프리팹을 Unity API로 읽었다. 닫힌 씬은 분리된 PreviewScene에서 읽고 닫았다. Play 중에는 PreviewScene을 열지 않았으며 사용자 Play를 중단하지 않았다. 마지막 검수는 Edit Mode에서 수행되어 생략 씬·씬 읽기 오류가 0이었다.

검수 전후 열린 씬 구성·활성 씬·startScene을 보존했고, 조사 기준의 자산·설정·기존 문서 1,999개 SHA-256은 모두 동일했다. 구조 검수의 실행 성공은 이동·스킬·카메라 전환 또는 빌드의 기능 통과가 아니다.

증거는 프로젝트 루트 기준 `output/Tech_SYM/audits/editor-entry-hms-2026-10-05/`의 `native-asset-inventory.json`, `serialized-inventory.json`, `component-audit-matrix.json`, `hms-reference-blueprint.json`, `system-spec-color-runs.json`, `readonly-audit-verification.json`이다. 상세 코드 검토와 변경 기능 검증은 구현 후 이 기록과 분리해 추가한다.
