# Feels Good Onion Project 개요

본 문서는 본 프로젝트의 개발 환경, 협업 전략, 브랜치 규칙 및 컨벤션을 정의한 가이드라인입니다. 본 프로젝트는 대학 학기작 프로젝트로 진행됩니다.

---

## 1. 개발 환경 및 언어

- **Unity 버전**: 6000.6.0f1
- **개발 언어**: 
  - C# (Unity 지원 닷넷 버전)
  - HLSL (사용 가능한 개발자 한정 적용)

## 2. 협업 전략 및 브랜치 관리

본 프로젝트는 소규모 개발 인원의 특성에 맞추어 유연하게 변형된 [GIT-FLOW 협업 전략](https://www.youtube.com/watch?v=EV3FZ3cWBp8&source_ve_path=OTY3MTQ&embeds_referring_euri=https%3A%2F%2Fvelog.io%2F)을 채택하여 관리합니다.

### 브랜치 규칙 및 사용자별 권한

첨부된 규칙 설정에 따라 각 브랜치별로 사용자 접근 권한과 룰이 엄격히 적용됩니다.

1. **메인 브랜치 규칙**
   - 첨부된 규칙 설정(`메인 브랜치 PR 규칙`)에 의거하여, `main` 브랜치는 직접적인 푸시가 불가능합니다.
   - 모든 변경 사항은 반드시 Pull Request를 거쳐야 하며, 강제 푸시(Force Push) 및 삭제가 차단됩니다.
   - [메인 브랜치 PR 규칙](https://github.com/CK2026-Team20/TitleProject/rules/22382772?ref=refs%2Fheads%2Fmain)

2. **직군별 브랜치 접근 제한 규칙**
   - 첨부된 규칙 설정(`타 직군 브랜치 접근 제한`)에 의거하여, 지정된 예외 권한을 가진 사용자 외에는 업데이트가 제한됩니다.
   - [타 직군 브랜치 접근 제한](https://github.com/CK2026-Team20/TitleProject/rules/22384476?ref=refs%2Fheads%2Fmain)

3. **아트 리소스 취합자 전용 규칙**
   - (이펙트 리소스 취합자)는 오직 `resources/assets` 브랜치에만 접근 및 작업이 허용됩니다.

## 3. 코딩 및 커밋 컨벤션

### C# 명명 규칙
프로젝트 내 모든 C# 스크립트 작성 시 아래의 공식 명명 규칙을 준수해야 합니다.
- [C# 명명 규칙](https://learn.microsoft.com/ko-kr/dotnet/csharp/fundamentals/coding-style/identifier-names)

### 커밋 메시지 컨벤션
모든 커밋 메시지는 아래의 표준 규칙을 따라야 합니다.
- [커밋 메시지 규칙](https://www.conventionalcommits.org/en/v1.0.0/)

#### 커밋 메시지 형식 리스트
- `feat`: 새로운 기능 추가
- `fix`: 버그 수정
- `docs`: 문서 수정
- `style`: 코드 포맷팅, 세미콜론 누락, 코드 변경이 없는 경우
- `refactor`: 코드 리팩토링
- `test`: 테스트 코드 추가 및 수정
- `chore`: 빌드 업무 수정, 패키지 매니저 수정 등 기타 작업

## 4. 폴더 명명 규칙 (Directory Naming Convention)

사용자 지정 폴더 명명 규칙은 추후 팀 회의를 통해 최종 확정될 예정이며, 현재 도식화된 양식은 다음과 같습니다. 커밋 메시지 컨벤션의 구조를 차용하여 직관적으로 구성합니다.

```text
Root/
└── Assets/
    ├── _Art/
    │   ├── Characters/
    │   │   ├── Animations/
    │   │   ├── Materials/
    │   │   ├── Models/
    │   │   └── Textures/
    │   ├── Environment/
    │   │   ├── Materials/
    │   │   ├── Models/
    │   │   └── Textures/
    │   └── UI/
    │       ├── Icons/
    │       └── Sprites/
    ├── _Audio/
    │   ├── Music/
    │   └── SFX/
    ├── _Code/
    │   ├── Assembly/
    │   ├── Core/
    │   │   └── Features/
    │   ├── Runtime/
    │   └── Utilities/
    ├── _Docs/
    ├── _Plugins/
    ├── _Prefabs/
    │   ├── Characters/
    │   ├── Props/
    │   └── UI/
    └── _Scenes/
        └── 01_Samples.unity
```

### 디렉터리 작업 제약 및 충돌 방지 규칙

협업 시 발생할 수 있는 깃(Git) 충돌 및 리소스 유실을 방지하기 위해 다음 제약 조건을 엄격히 준수합니다.

1. **씬(Scene) 파일 접두사 넘버링 필수**
   * `_Scenes` 폴더 하위에 생성되는 모든 Scene 파일은 반드시 `01_Test`, `02_Main`과 같이 두 자리 숫자의 접두사 넘버링을 포함해야 합니다.
   * 이는 씬 파일의 용도와 로드 순서를 직관적으로 파악하고, 빌드 셋팅 시의 인덱스 혼선을 방지하기 위함입니다.

2. **동일 디렉터리 동시 작업 시 개인 폴더 격리**
   * 부득이하게 같은 폴더 공간에서 여러 명이 동시에 작업해야 할 경우, 해당 디렉터리 하위에 **작업자의 직군과 이름을 조합한 상위 폴더** (**예: `Tech_OOO`, `Art_OOO`**)를 임시로 생성합니다.
   * 각 작업자는 할당된 개인 폴더 내부에서만 리소스 및 스크립트를 생성/수정하며, 최종 테스트가 완료된 후 공용 폴더로 병합(Merge)합니다.

3. **프리팹(Prefab) 원본 직접 덮어쓰기 금지**
   * `_Prefabs` 하위에 위치한 공용 프리팹을 여러 명(특히 프로그래머와 AD)이 동시에 열어 수정하는 것을 엄격히 금지합니다.
   * 변경 사항이 있을 경우, 원본을 직접 수정하지 않고 씬에 꺼내어 테스트용으로 수정한 뒤 변경점만 적용(Apply)하거나, 시각(Visual)용 프리팹과 논리(Logic)용 프리팹을 중첩(Nested Prefab)하여 참조하는 방식으로 작업 영역을 분리해야 합니다.

4. **파일 이동 및 삭제 시 유니티 에디터 사용 필수**
   * 윈도우 탐색기나 외부 환경에서 에셋 파일의 이동, 이름 변경, 삭제를 절대 금지합니다.
   * 반드시 **유니티 에디터 프로젝트(Project) 창 내부에서 수행**하여 `.meta` 파일이 누락되거나 씬, 프리팹에서의 참조가 끊어지는(Missing Reference) 치명적인 오류를 방지해야 합니다.

5. **서드파티 플러그인 에셋 격리**
   * 에셋 스토어에서 다운로드한 외부 플러그인이나 라이브러리는 무조건 `_Plugins` 폴더 내부에만 위치시킵니다. 
   * 프로젝트 내부에서 자체 개발한 `_Code` 또는 `_Art` 리소스 경로와 섞이지 않도록 폴더를 분리하여 의도치 않은 코드 종속성과 파일 덮어쓰기를 방지합니다.

## 6. [Cooked!](./Assets/_Docs/Cooked!제안서.pdf) 창작 게임 기획 제안서 및 핵심 시스템 명세

제안서 "Cooked!"의 주요 기획 양상과 핵심 시스템 명세서를 요약 및 재구성한 내용입니다.

### 1. 게임 기본 정보 및 컨셉
* **게임명**: Cooked!
* **장르**: 3D 플랫포머, 어드벤처
* **플랫폼**: PC
* **엔진**: Unity
* **시각적 컨셉**: 거대한 주방 안의 작고 둥글둥글한 식재료 시점. 아기자기하고 파스텔 톤의 캐주얼한 분위기와 비정상적으로 변화하는 형태의 '버그' 시각화 결합.
* **시놉시스**: 인간 플레이어가 게임을 종료하면 살아 움직이는 요리 게임 속 세계. 양파 캐릭터 '어니'가 업데이트로 인해 곧 삭제될 버그 난 주방 스테이지에 갇힌 감자 친구 '포포'를 구출하고 탈출하는 이야기.

---

### 2. 핵심 시스템 및 기능 명세서

플랫포머 어드벤처의 재미를 극대화하기 위해 캐릭터의 특성과 버그 환경을 결합한 5가지 주요 시스템으로 구성됩니다.

#### 양파 껍질 시스템 (크기 전환 및 상호작용)
주인공 '어니'의 핵심 플랫포밍 기믹으로, 양파가 껍질을 벗는 특성을 활용한 상태 전환 시스템입니다.
* **상태별 특징**:
  * **큰 상태 (Default)**: 무게 장치 작동 가능, 부서지는 바닥을 파괴할 수 있음.
  * **작은 상태**: 좁은 틈새 통과 가능, 부서지는 바닥을 무너뜨리지 않고 이동 가능.
* **기능 메커니즘**:
  * `큰 상태 -> 작은 상태` 전환 시: 현재 위치에 '벗겨진 껍질' 오브젝트가 남음. 이 껍질은 무게 스위치를 누르는 등의 환경 상호작용(발판/압력 유지)에 활용됨.
  * `작은 상태 -> 큰 상태` 전환 시: 캐릭터가 큰 상태로 복원되며, 기존에 월드에 남겨두었던 껍질은 사라짐.
  * 남용 방지를 위해 상태 재전환 시 짧은 쿨타임(제한) 적용.

#### 눈물 능력 시스템 (군중 제어/보조 기능)
양파의 매운맛으로 인해 눈물이 나는 특성을 활용한 회피형 보조 스킬입니다.
* **기능 메커니즘**: 능력 사용 시 일정 범위 내의 작은 버그 생명체들에게 '눈물 효과'를 부여하여 일정 시간 동안 행동 불가(기절/무력화) 상태로 만듦.
* **제약 사항**: 버그를 영구적으로 처치할 수는 없으며, 쿨타임을 길게 설정하여 난이도 하락을 방지하고 전략적인 회피 수단으로만 사용하도록 제한함.

#### 환경 및 버그 시스템 (레벨 디자인 기믹)
주방 오브젝트들에 프로그래밍적 오류(버그)가 발생했다는 설정으로, 이를 활용해 길을 개척합니다. (자동 반복 작동)
* **복제 오류**: 식빵 등 특정 오브젝트가 비정상적으로 무한 생성 및 누적됨. (쌓인 오브젝트를 계단으로 활용)
* **크기 오류**: 과도하게 거대해진 음식 모델링을 지형이나 발판으로 활용.
* **부유(중력) 오류**: 물리 법칙을 무시하고 공중에 떠 있는 접시나 기물들을 징검다리 발판으로 활용.
* **루프(위치) 오류**: 특정 구간을 비정상적으로 왕복하는 오브젝트의 타이밍을 파악해 이동.

#### 조리 디버프 시스템 (캐릭터 상태 변화)
특정 주방 환경과 접촉 시 식재료인 캐릭터에게 특수한 물리적 상태(디버프)가 강제 부여되는 시스템입니다.
* **기능 메커니즘 (기름 디버프)**: 프라이팬의 기름 등 특정 환경을 밟을 경우, 어니의 몸에 기름이 묻어 '미끄러운 상태'로 전환됨.
* **효과**: 이동 시 제동력이 크게 감소하여 미끄러지며 조작감이 변화함. 해당 환경을 벗어나도 일정 시간 동안 효과가 유지되어 이후 플랫포밍 난이도에 영향을 줌.

#### 추격 시스템 (긴장감 조성 기믹 - *후순위 구현*)
게임 후반부에 다수의 버그 떼(단일 개체로 판정)가 플레이어를 추격하는 클라이맥스 시스템입니다.
* **기능 메커니즘 (3-Strike 아웃)**: 즉사기가 아닌 '거리 누적형' 실패 방식을 채택.
* 정상적으로 이동 시 거리가 유지되거나 멀어지지만, 장애물 충돌 등 1번 실수 시 거리가 좁혀지고, 3번의 누적 실수가 발생하여 완전히 따라잡히면 플레이 실패(Game Over) 처리됨.
